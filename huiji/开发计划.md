# 灰迹输入法 · 开发计划

这份计划回答一个问题：**从现在到做出能用的输入法，具体怎么走。**

它是照着推进的工作底稿，不是对外介绍。时间数字都是**【测算】**，按“个人业余、每周 10–15 小时、AI 辅助”估的，投入得多就快、卡住就慢，别当承诺。为什么做、市场如何，见《开发前提.md》，这里只讲怎么做。

---

## 一、六个阶段，三道门

```
阶段0 准备       搭环境、fork、跑通编译
阶段1 地基探针    改一个小东西，证明能在青简上动手
       ──────── 第 1 道门：能安全做增量 ────────
阶段2 原型验证    整句翻译、手误纠错各做最小原型
       ──────── 第 2 道门：两个能力成不成立 ────────
阶段3 Windows MVP 把成立的能力拼成能用的输入法
       ──────── 第 3 道门：自己日常敢不敢用 ────────
阶段4 打磨内测    修问题、补体验、给少数人试用
阶段5 跨平台发布  macOS / Linux、开源、签名
```

前两道门是**止损点**，门没过就停下重新商量，不硬着头皮做。输入法最怕闷头干半年，回头发现核心功能根本不达标。

**耗时一览【测算】**：准备 3–7 天；地基探针 2–4 天；原型 2–5 周；Windows MVP 3–6 周；打磨 3–6 周；跨平台 4–8 周。做到 Windows 日常能用约 **2–4 个月**，三平台再加 1–2 个月。除签名外基本不花钱。

---

## 二、阶段 0：准备（3–7 天）

不写功能，把“工作台”搭好，确认青简在你机器上能编译、能改。

- 装 Rust 工具链，以及 Windows 必需的 MSVC 生成工具；
- 把青简 fork 到你自己账号（要你操作，我提示）；
- 克隆到项目的 `app/` 子目录，和文档分开；
- 不改代码，先把原版编译一遍、确认能出包；
- 初始化 git、配好提交习惯；列一张品牌替换清单先标记。

**过关**：原版能编译、能出包。编译不过先解决环境，别往下。Rust 在 Windows 首次构建要编很多依赖，慢是正常的。搭环境这种容易出岔子的脏活交给我，我读报错、我修。

---

## 三、阶段 1：地基探针（2–4 天）

做一个**小到不可能失败**的改动，验证整条链路：改代码 → 编译 → 安装 → 在系统里生效。挑肉眼可见、不碰核心逻辑的地方，比如某个提示文字、设置页标签、候选词默认个数。改完出包、安装，截图确认改动真的出现。

**过关**：能在装出来的输入法里明确看到那处改动，后面所有功能都能照这个循环往里加。

**第 1 道门**：改个小地方都牵一发动全身、无从下手，就重新评估切入点。

---

## 四、阶段 2：原型验证（2–5 周，最关键）

不追求完整，只回答两个问题：**整句翻译能不能用？手误纠错提升多大？** 两个原型分开做、互不阻塞。

### 2A 整句翻译

- **云端探针**：复用青简云联想通道接翻译接口，先跑通“一句中文 → 整句英文”；
- **端侧探针**：本地集成离线翻译（NLLB 蒸馏等，量化后用 FFI 接进 Rust）；
- 建 **100 个真实句子**的测试集，覆盖日常、工作、口语、长句、网络用语，别只用“你好谢谢”；
- 测两件事：质量（人工读、打分）和延迟（多看几句的中位数，别只看最快的一次）。

定路线：端侧延迟中位数能压到约 **800ms**、质量多数可读，端侧做默认、云端可选；端侧太慢或读不通，默认走云端、端侧只兜短句；两条都不理想，先保住青简原有的单词译词。

### 2B 手误纠错

- 建 **500–1000 条**“手误 → 正确”对照，真人常犯加**合成**（按相邻键和常见拼音混淆自动造错）；
- 实现规则层（编辑距离、模糊音、相邻键权重），Rime 和四叶草的规则直接参考；
- 同一批手误让原版和增强版各给首选，重点盯**误改**，尤其是人名、专名。

值得做的门槛：增强后首选命中率比基线提升约 **10 个百分点**、误改不增加，就进 MVP；提升不明显只留模糊音规则；误改变多就调保守、宁可提示不自动改。

**第 2 道门**：阶段末手里有真实的质量分、延迟、命中率，靠数据定 MVP 放什么，不接受“感觉应该可以”。

---

## 五、阶段 3：Windows MVP（3–6 周）

原型过了才进，目标是做一个**你自己愿意天天用**的 Windows 输入法。

**必做**：继承青简拼音、候选、单词译词；验证成立的整句翻译和纠错（高置信才改、低置信只提示、改了能撤销）；自有品牌的名称、图标、设置页；基础设置（中英切换、候选数、主题、云开关）。

**先不做**：更多语言对、皮肤商城、跨平台、账号同步、语音输入。

新增能力做成独立模块，别搅成一团。**真机验证这步 AI 替不了**：系统记事本、浏览器、Office、聊天软件、Electron、商店应用都过，测中英混输、快速打字、长用后的内存、断网下的基础输入、候选框位置和翻页。虚拟注入的键青简不消费，打字手感你来，我负责截图、读日志。

**过关（第 3 道门）**：你愿意设成默认、连续用一周，该打的都能打、不闹心。自己都不愿用，就别急着给别人。

---

## 六、阶段 4：打磨内测（3–6 周）

自己用顺了，再给一小圈人，别急着公开。

要补：个性化学习（数据留本地）、纠错的撤销和“记住这类别再改”、译文独立面板和快捷键、主题字号、安装引导（写明注销重登生效、SmartScreen 怎么点过去）。

内测找 10–20 个能容忍 bug 的技术爱好者，反馈按严重度收口、先修没法用和影响体验的；重点问两件事：**有没有帮倒忙（误改）、翻译读不读得通**，这是本项目的命门。

---

## 七、阶段 5：跨平台与开源（4–8 周，可延后）

Windows 站稳了再考虑，别一开始三线作战。

做 macOS、Linux（Fcitx5）适配（青简有前端能省事，但坑得逐个真机过）；开源合规自查；签名、定分发渠道；写用户说明和贡献者文档。

**合规清单**：保留青简版权和 GPL、我们代码同样开源；名称图标完全自有、只在致谢提青简；逐个核对词库模型许可、确认能再分发；说明默认离线、云功能默认关。

**签名自己决定**：不签名能发、Windows 提示未知发布者，内测开源一般能接受；Windows 证书约 ¥500–2000/年【测算】，macOS 正规分发再加 Apple US$99/年，纯开源直发可以不签。

---

## 八、工程规范

- 本地**频繁小提交**，一个能跑的改动就提交，别攒；没确认不推 GitHub，确认再推、重要节点打 tag；改坏用 git 回退，不手动硬救。
- 提交前过 `cargo fmt` 和 `cargo clippy`；核心逻辑（编辑距离、切分、排序）尽量写单测；日志别把用户输入内容随便记。
- 源码在 `app/`，评测、品牌素材各归各位，以 fork 下来的实际结构为准。

---

## 九、AI 协作流程

标准循环：你说清要什么 → 我动手、产出能运行能看见的结果 → 截图或真机确认 → 你认可就提交，不认可我改。

原则：

1. **一次只做一个能验证的小目标**，别让我一口气做完，大改没法验证；
2. 环境、报错、样板、脏活累活全交给我；
3. 真机测试、产品取舍、最终拍板你来，我给方案和数据；
4. 关键结论看实测，我不拿“应该行”交差；
5. 跑偏了随时打断、回退到上个能跑的版本，重来成本低。

你不用先系统学 Rust，边做边补，但始终要看懂两件事：**数据在模块间怎么流动、当前这步在解决什么问题**。语法细节不用管，这两点清楚，项目就不会变成你接不住的黑盒。

## 十、风险与应对

| 风险 | 应对 |
|---|---|
| 端侧翻译又慢又差 | 退回云端可选，端侧只兜短句 |
| 纠错提升小还误改 | 只留模糊音、调保守、重提示 |
| 数据拼不过商业输入法 | 强化本地学习加云端兜底，不正面拼全能 |
| 跨应用兼容问题 | 列清单逐个修、优先高频应用 |
| 范围越做越大 | 守住必做项，新想法往后排 |
| 精力跟不上 | 缩小范围，先把 Windows 做扎实 |
| AI 给的实现不工作 | 小步验证，每步必须能运行、能回退 |

每个阶段留约 **20%–30% 的时间缓冲**【测算】，新手加系统级开发，意料之外的坑不会少。
