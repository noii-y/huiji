# 灰迹输入法 · 开发计划

这份计划回答一个问题：**从现在到做出能用的输入法，具体怎么走。**

它不是写给外人看的介绍，是我们俩照着推进的工作底稿。每个阶段都列了要做的事、做完长什么样、怎么算过关、大概花多久。时间数字都是**【测算】**，按"个人业余、每周 10–15 小时、AI 辅助"估的，你投入得多就快，中途卡住就慢，别把它当承诺。

配套的《开发前提.md》讲清楚了为什么做、市场什么情况，这里不重复，只讲怎么做。

---

## 一、总览：六个阶段，三道门

```
阶段0 准备        搭环境、fork、跑通编译
阶段1 地基探针     改一个小东西，证明能在青简上动手
        ───────── 第 1 道门：能安全做增量 ─────────
阶段2 原型验证     整句翻译、手误纠错各做一个最小原型
        ───────── 第 2 道门：两个能力到底成不成立 ─────
阶段3 Windows MVP  把成立的能力拼成一个能用的输入法
        ───────── 第 3 道门：自己日常敢不敢用 ─────────
阶段4 打磨内测     修问题、补体验、给少数人试用
阶段5 跨平台发布   macOS / Linux、开源、签名
```

前两道门是"止损点"。门没过就停下来重新商量，不硬着头皮往下做。这样最省时间——做输入法最怕闷头干半年，回头发现核心功能根本不达标。

**各阶段耗时一览【测算】**

| 阶段 | 主要内容 | 预计耗时 | 要不要花钱 |
|---|---|---|---|
| 0 准备 | 环境、fork、编译 | 3–7 天 | 0 |
| 1 地基探针 | 一个最小改动 | 2–4 天 | 0 |
| 2 原型验证 | 翻译 + 纠错原型 | 2–5 周 | 0–几十元 |
| 3 Windows MVP | 完整可用版 | 3–6 周 | 0，签名可选 |
| 4 打磨内测 | 体验、修 bug | 3–6 周 | 0–少量 |
| 5 跨平台发布 | 多平台、开源 | 4–8 周 | 0，签名可选 |

做到 Windows 上自己日常能用，大概 **2–4 个月【测算】**。三平台都做，再加 1–2 个月。

## 二、阶段 0：准备（3–7 天）

这一阶段不写功能，目标是把"工作台"搭好，确认青简这份代码在你机器上能编译、能改。

### 任务清单

- [ ] 确认电脑装了 Rust 工具链：`rustup`、`cargo`，以及 Windows 上必需的 MSVC 生成工具（Visual Studio Build Tools，勾选 C++ 桌面开发）。
- [ ] 在 GitHub 上把 `qingjian-team/qingjian` **fork 到你自己的账号**。这一步要你的 GitHub 账号，到时我提示你操作。
- [ ] 把 fork 克隆到本地项目文件夹里的 `app/` 子目录（和文档分开，别混在一起）。
- [ ] **不改动任何代码**，先按青简的构建说明把原版编译一遍，确认能出包。
- [ ] 初始化本地 git，配好提交习惯（见第八节）。
- [ ] 列一张"品牌替换清单"：哪些地方出现了"青简"字样、图标在哪、版本信息在哪，先标记，不急着改。

### 做完应该看到

- 命令行里 `cargo build` 能跑完，不报错；
- 本地能生成一个和你现在装的青简一样的安装包（哪怕先不装）；
- 项目文件夹结构清楚，源码在 `app/`，文档在外面。

### 怎么算过关

原版能编译、能出包。如果连原版都编译不过，先解决环境，别往下走。Rust 在 Windows 上首次构建会下载、编译很多依赖，慢是正常的，等就行。

> 头一回搭 Rust + MSVC 环境对新手最容易出岔子，这部分你直接交给我，我读报错、我修，你在旁边看个大概就好。

## 三、阶段 1：地基探针（2–4 天）

编译跑通后，先做一个**小到不可能失败**的改动，目的是验证整条链路：改代码 → 编译 → 安装 → 在系统里生效。

### 做什么

挑一个肉眼能看见、又不影响核心逻辑的地方，比如：
- 候选框里某个提示文字；
- 设置页里一个标签；
- 候选词的默认个数（先改个明显的值）。

改完重新出包、安装，截图确认改动真的出现了。

### 怎么算过关

你能在装出来的输入法里，明确看到我们改的那一处。这一步过了，说明后面所有功能都能照这个循环往里加，心里有底。

**第 1 道门**：如果改个小地方都牵一发动全身、青简代码完全无从下手，那就得重新评估——是先补一补 Rust，还是换更模块化的切入点。

## 四、阶段 2：原型验证（2–5 周，最关键）

这个阶段不追求完整，只回答两个问题：**整句翻译能不能用？手误纠错提升有多大？** 两个原型可以分开做、互不阻塞。

### 2A 整句翻译原型

#### 要做的事

1. **云端探针**：复用青简已有的云联想通道（默认关闭、用户自填服务商那套），接一个翻译接口，输入一句中文，拿到整句英文译文。先把这条链路跑通。
2. **端侧探针**：在本地集成离线翻译。候选是 Argos Translate 或 NLLB-200 蒸馏模型，配合 CTranslate2 量化，用 FFI 接进 Rust。
3. **建测试集**：准备 100 个真实句子，别只用"你好""谢谢"这种。要包含日常聊天、工作、口语、长句、网络用语，尽量像真人会打的东西。
4. **测两件事**：译文质量（人工读、打分）和延迟（从发起到出译文多少毫秒，多测几句看中位数，别只看最快的一次）。

#### 记录表格（每句一行）

| 编号 | 中文原句 | 场景 | 云端译文 | 云端延迟(ms) | 端侧译文 | 端侧延迟(ms) | 质量分(1–5) | 备注 |
|---|---|---|---|---|---|---|---|---|
| 1 |  |  |  |  |  |  |  |  |

质量分自己定标准，简单点：5 通顺准确、3 能猜懂但别扭、1 完全不能用。

#### 怎么定路线（决策规则，门槛可商量）

- 端侧延迟中位数能压到 **800ms 以内【建议值，实测后调整】**、质量分多数在 3 分以上 → 端侧可作为默认，云端作为可选增强；
- 端侧太慢或读不通 → 默认走云端（用户主动开启），端侧只做短句兜底，或者干脆第一版不做端侧；
- 两条路都不理想 → 整句翻译降级，先保住青简原有的单词译词。

### 2B 手误纠错原型

#### 要做的事

1. **建评测集**：500–1000 条"手误 → 正确"的对照。来源两块：
   - 真人常犯的（漏字母、多字母、按错相邻键、拼音混淆）；
   - **合成**：拿正常句子，按 QWERTY 相邻键和常见拼音混淆（zh/z、n/l、前后鼻音等）自动"制造错误"。
2. **实现规则层**：编辑距离 + 模糊音 + 相邻键权重。Rime 的 `speller/algebra` 和四叶草拼音的纠错规则可以直接参考，不用自己从零想。
3. **对比**：同一批手误，分别让青简原版和我们的增强版给首选，看谁更接近正确答案。
4. 重点盯**误改**：本来打对的，有没有被我们"纠正"成错的，尤其人名、专名。

#### 记录表格

| 编号 | 手误拼音 | 正确目标 | 青简首选 | 增强首选 | 增强是否命中 | 有没有误改 |
|---|---|---|---|---|---|---|
| 1 |  |  |  |  |  |  |

#### 怎么算值得做

- 增强后首选命中率比青简基线**提升 10 个百分点以上【建议门槛】**，同时误改不增加 → 做进 MVP；
- 提升不明显 → 只保留成熟的模糊音规则，别硬上复杂模型；
- 误改明显变多 → 把纠错调更保守，宁可提示、不自动改。

**第 2 道门**：这一阶段结束，我们手里有真实的质量分、延迟、命中率，靠这些数据决定 MVP 里到底放什么。所有结论都要能在记录表格里翻到出处，不接受"感觉应该可以"。

## 五、阶段 3：Windows MVP（3–6 周）

原型验证过了，才进入这一步。目标是做一个**你自己愿意天天用**的 Windows 输入法。

### 功能取舍

**必做（P0）**
- 继承青简的拼音输入、候选、单词译词；
- 阶段 2 验证成立的整句翻译（按选定的路线）；
- 验证成立的纠错增强，遵循"高置信才改、低置信只提示、改了能撤销"；
- 自有品牌：名称、图标、设置页，不出现青简名号和 logo；
- 基础设置项：中英切换、候选个数、主题、云开关。

**先不做（P1，往后放）**
- 更多语言对、皮肤商城、跨平台、账号同步、语音输入。

### 模块怎么分

沿用青简"后台服务 + TSF 前端 + 命名管道"的结构，新增能力尽量做成独立模块，别把代码搅成一团：

| 模块 | 职责 |
|---|---|
| server | 常驻、调度、管数据和模型 |
| TSF 前端 | 收键、上屏、候选 UI |
| 翻译模块 | 云端/端侧调用、译文缓存 |
| 纠错模块 | 拼音容错、候选重排 |
| 数据/模型 | 词库、语言模型、用户学习数据 |
| 设置 | 配置读写、界面 |

### 真机验证（这步 AI 替不了）

输入法是系统级的东西，必须在真实环境里、用真实键盘测。重点过这些场景：
- 系统记事本、浏览器、Office、微信/QQ、Electron 应用、商店应用；
- 中英文混输、快速打字、长时间使用后的内存占用；
- 断网状态下基础输入和译词还正不正常；
- 候选框位置、会不会挡住内容、翻页顺不顺。

虚拟键盘注入的按键青简不消费（前面踩过坑），所以"打字手感"这部分得你来，我负责截图看界面、读日志排查。

### 怎么算过关

你愿意把它设成默认输入法，连续用一周，日常该打的东西都能打、不闹心。**第 3 道门**就看这个——自己都不愿用，就别急着给别人。

---

## 六、阶段 4：打磨与内测（3–6 周）

自己用顺了，再给一小圈人用，别急着公开。

### 要补的东西

- 个性化学习：记住你的常用词、输入习惯（数据留在本地）；
- 纠错的"记住这类别再改 / 撤销"；
- 整句译文的独立面板和快捷键；
- 主题、字号、常用设置补齐；
- 安装引导：写明"注销重登后生效"、SmartScreen 未知发布者怎么点过去。

### 内测怎么组织

- 找 10–20 个能容忍 bug、愿意反馈的人，优先技术爱好者；
- 反馈统一收口，按严重程度分三类：没法用的、影响体验的、锦上添花的，先修前两类；
- 重点问两件事：**有没有帮倒忙（误改）、翻译读不读得通**。这两个是本项目的命门。

## 七、阶段 5：跨平台与开源发布（4–8 周，可延后）

Windows 站稳了再考虑别的，别一开始就三线作战。

### 要做的事

- macOS、Linux（Fcitx5）适配，青简本身有这两端的前端，能省不少事，但坑得逐个真机过；
- 开源合规自查（清单见下）；
- 代码签名、确定分发渠道；
- 写一份给用户看的说明和给贡献者看的文档。

### 开源合规清单

- [ ] 保留青简的版权与 GPL-3.0 许可声明，我们的代码同样以 GPL 开源；
- [ ] 名称、图标完全自有，只在"致谢"里提到基于青简；
- [ ] 逐个核对词库、语言模型、翻译模型的许可，确认能再分发；
- [ ] 说明数据怎么处理：默认离线、云功能默认关闭。

### 签名这笔钱（自己决定要不要花）

- 不签名：能发，Windows 会提示未知发布者，内测和开源用户一般能接受；
- Windows OV 签名证书：约 **¥500–2000/年【测算，以实际报价为准】**，装的时候不报警；
- macOS 要分得正规，再加 Apple Developer **US$99/年**；纯开源直发可以不签。

## 八、工程规范

这些规矩现在定好，后面少返工。

### 目录结构（建议）

```
灰迹输入法/
├─ 开发前提.md
├─ 开发计划.md
├─ app/                  # fork 来的青简源码（cargo 项目）
├─ docs/
│  ├─ 评测/              # 翻译、纠错的评测记录
│  └─ 决策记录/          # 每道门怎么定的
└─ assets/               # 自有图标、品牌素材
```

实际以 fork 下来的青简结构为准，不强求。

### git 习惯（沿用你"先本地、确认后推送"的规矩）

- 本地**频繁小提交**，一个能跑的改动就提交一次，别攒一大堆；
- 只在本地改、没确认前，**不往 GitHub 推**；
- 确认没问题了再推送，重要节点打 tag；
- 改坏了用 git 回退，不手动硬救。

### 代码质量

- 提交前过一遍 `cargo fmt`（格式）和 `cargo clippy`（常见问题）；
- 能写单元测试的核心逻辑（编辑距离、切分、候选排序）就写，后面改起来不慌；
- 日志留好，但别把用户输入内容随便记下来，和隐私承诺保持一致。

## 九、AI 协作流程（怎么用我最省事）

一个标准循环，每个阶段都这么走：

```
你说清这一步要什么
   → 我动手（写代码 / 跑命令 / 改东西）
   → 产出一个能运行、能看见的结果
   → 截图或真机确认
   → 你认可 → git 提交；不认可 → 我改
```

几条原则：

1. **一次只做一个能验证的小目标**。别让我"一口气把输入法做完"，大改没法验证，最容易出看似能用、实际不工作的东西。
2. **环境、报错、样板代码、脏活累活全交给我**。
3. **这几件事你来**：真机和真实键盘测试、产品取舍、最终拍板。我给方案和数据，决定你做。
4. **关键结论看实测**：翻译质量、延迟、纠错率，以记录表格为准，我不拿"应该行"交差。
5. 我要是跑偏了或者你觉得方向不对，随时打断，回退到上个能跑的版本，重来成本很低。

你不用先系统学 Rust 再开工，边做边补就行。但建议你始终能看懂两件事：**数据在模块间怎么流动、当前这一步在解决什么问题**。语法细节不用管，这两个清楚，项目就不会变成你接不住的黑盒。

## 十、风险和应对

| 风险 | 早期信号 | 怎么应对 |
|---|---|---|
| 端侧翻译又慢又差 | 原型阶段延迟高、评分低 | 退回云端可选，端侧只做短句或暂缓 |
| 纠错提升小、还误改 | 评测命中率上不去、误改增多 | 只留模糊音规则，调保守，强调提示而非自动改 |
| 数据打不过商业输入法 | 网络新词、个性化表达总出错 | 强化本地个性化学习 + 云端兜底，不正面拼全能 |
| 跨应用兼容问题 | 某个常用 App 里不出候选或崩溃 | 列兼容清单逐个修，优先覆盖高频应用 |
| 范围越做越大 | 不断往里加功能、迟迟出不了 MVP | 守住 P0，新想法记下来往后排 |
| 个人精力跟不上 | 进度长期停滞 | 缩小范围，先把 Windows 单平台做扎实 |
| AI 给的实现不工作 | 编译过了但实际没效果 | 小步验证，每步必须可运行、可回退 |

时间上给每个阶段留约 **20%–30% 的缓冲【测算】**，新手 + 系统级开发，意料之外的坑不会少。

## 附录：术语速查

| 词 | 简单解释 |
|---|---|
| TSF | Windows 的文本服务框架，现代输入法必须挂在它上面，本质是 COM 组件 |
| TIP | TSF 里的一个具体输入法，有唯一 CLSID |
| CLSID | COM 组件的唯一编号 |
| NMT | 神经机器翻译，用神经网络做翻译 |
| NLLB | Meta 的多语言翻译模型，蒸馏版更小更快 |
| CTranslate2 | 跑 Transformer 模型的高效推理引擎，能量化、加速 |
| BLEU | 翻译质量的一种自动评分，只作参考，不同语言不能直接比 |
| n-gram | 基于相邻词统计的语言模型，输入法常用 |
| 编辑距离 | 两个字符串之间差几个操作（增、删、改、换位） |
