## 1. 项目背景与定位

### 1.1 缘起

在使用开源拼音输入法 **青简（qingjian）** 后，认可其"本地优先、隐私、候选词旁显示学习语言译词"的设计，但发现两个明显可优化点：

1. **只能翻译单词/词组，不能翻译整句**——打出一个完整句子时，无法得到整句译文；
2. **手误情况下的意图匹配能力不足**——拼错、漏字母、按错相邻键时，给出用户真正想要的词的能力有待提升。

由此希望以青简为**基石**并向其致敬，同时糅合搜狗、Windows 自带输入法等成熟产品的优点，做一款全新输入法，工作名 **「灰迹」**。

### 1.2 一句话定位

> 一款**隐私优先、离线可用、无广告、轻量**的拼音输入法，在青简"译词"基因之上，提供**整句翻译**与**恰到好处的手误纠错**。

### 1.3 关键判断（先给结论）

- 输入法**最难的系统集成层**（Windows TSF、候选渲染、本地模型管线、跨平台）青简已经趟平，**应站在其肩膀上做增量，而非从零重写**。
- 整句翻译主要是**路线选择 + 工程优化**问题（云端质量高、端侧保隐私），可行性较高。
- 意图纠错的算法成熟、可改进，但其**天花板取决于训练数据规模**——这是与搜狗/微软差距最大、也最难弥补的地方。
- 市场存在明确空白：**隐私 + 无广告 + "纠错中间档"**，这是比"再做一个大而全输入法"更现实的差异化切口。

### 2.2 技术架构（前后端分离）

青简采用"**后台服务进程 + 各平台输入法前端 + 本地数据/模型**"的分离架构：

- **后台服务**：`qingjian-server.exe`，通过**命名管道** `\\.\pipe\qingjian` 与前端通信（非 TCP 端口）。
- **输入法前端**：Windows 上为 TSF（Text Services Framework）COM DLL；macOS/Linux 各有前端。
- **本地数据**：词库、语言模型、领域词库（成语/动物/IT/医学等）。
- **整句神经模型**：用于拼音串→汉字的候选重排（是语言模型，**不是翻译模型**）。
- **云联想通道**：**默认关闭**，用户可自填 AI 服务商地址，请求不经过青简服务器——这是后续做"云端整句翻译/兜底纠错"可直接复用的通道。

### 2.4 青简的能力边界

**已具备**：本地拼音→字词/整句候选、候选词旁显示学习语言译词、n-gram + 神经整句重排、个人词库/词频学习、中英切换、跨平台前端、可选云联想。

**不具备/不足（本项目机会点）**：
- 无**整句翻译**（仅单词/词组译词）；
- 手误纠错、模糊音、相邻键错按、个性化意图推断**较弱**；
- Windows 仍处测试阶段，部分应用兼容性待打磨。

> **验证注意（已踩坑）**：通过虚拟光标/RPA 注入的按键事件不被青简 TSF 消费（会直接上英文、日志无收键记录）；验证真实打字效果需用**真实键盘**或目视截图，不能依赖自动化"打字"。

## 3. 市场与竞品分析

### 3.1 商业输入法现状（2025–2026）

| 产品 | 现状与技术方向 | 对本项目的启示 |
|---|---|---|
| 搜狗输入法 | 2026-01 发布 **20.0 全面 AI 化**，AI 用户破亿、日均语音近 20 亿次；AI 翻译接入腾讯混元翻译模型、支持 30 多种语言输入即译；自研 AI 打字大模型；逻辑从"以词库为核心"转向"**词库为基础 + 生成为核心**"；提供医生/律师等专业定制 | 整句、意图、翻译都在走向大模型；但其**广告、弹窗、臃肿**也最被诟病 |
| 微软拼音 | 系统级集成、稳定、安静、无广告；整句与云能力相对克制 | "稳定、安静、系统级可靠"是值得继承的优点 |
| 微信输入法 | 接入混元大模型，多端协同；但被吐槽联想弱、网络用语少、关键词疑似用于广告 | 生态绑定带来信任顾虑 |

**搜狗云输入的经典做法**：在特定条件下把计算放到服务器，云端结果显示在**第二个候选位**，长句准确率明显高于本地——这是"本地候选 + 云端兜底"交互范式的成熟参照。

### 3.2 开源输入法/引擎对比

| 引擎/项目 | 架构 | 许可 | 特点 | 局限 |
|---|---|---|---|---|
| **青简 qingjian** | server + TSF/前端 + 本地模型（Rust） | GPL-3.0 | 译词基因、本地优先、跨平台、含云联想通道 | 很新；无整句翻译；纠错弱 |
| **Rime / 中州韵** | `librime` 核心库（C++）+ plum 配置 + 平台前端（Weasel/Squirrel/ibus-rime）；前后端分离 | BSD（引擎） | 高度可定制、YAML 输入方案、热加载、管线含 Processors/Segmentors/**Translators**、插件化 | 本质是"引擎"，无自带方案/词库，需折腾 |
| **Mozc**（Google 日语） | 转换引擎 + 语言模型 + 系统/用户词典 + 预测 | BSD-3 | 转换准确率高、工程成熟 | 面向日语；云同步为专有版 |
| libpinyin / Google 拼音等 | 句库 + 语言模型 | 各自开源 | 经典整句算法参考 | 维护活跃度不一 |

> **架构共识**：成熟开源输入法普遍采用"**核心引擎/服务 与 平台前端分离**"，青简与 Rime 皆是如此——这印证了我们沿用并强化该架构的合理性。

## 5. 产品定义

### 5.1 价值主张

1. **可信**：默认离线、本地优先、零广告、单一职责，数据归属用户；
2. **懂你**：恰到好处的纠错与意图匹配，改错有边界、可回退；
3. **跨语言**：从"译词"进化到"整句翻译"，离线可兜底、云端可选；
4. **轻快**：常驻低占用、响应即时。

### 5.2 功能范围（分档，避免一上来铺太大）

| 档位 | 内容 |
|---|---|
| **MVP（必做）** | ① 继承青简基础拼音输入与译词；② **整句翻译最小闭环**（先打通一种路线）；③ **保守可控的手误纠错**（模糊音 + 相邻键 + 编辑距离 + 一键提示）；④ 基础设置与品牌替换；⑤ Windows 单平台 |
| **增强（其后）** | 个性化词库/句模学习、更强端侧语言模型、整句译文独立面板与快捷键、皮肤/主题、更多语言对、云端兜底（用户自填） |
| **非目标（明确不做）** | 广告与广告联盟、信息流/内容商城、与输入无关的全家桶功能、默认上传输入内容、强制账号体系 |

### 5.3 "好"的决策标准（可观察，6–10 条）

1. **默认零网络也能完成"拼音→汉字"与基础译词**；任何联网功能默认关闭且有明确开关与提示。
2. **按键到候选的响应**在普通机器上保持即时（无明显卡顿），重模型懒加载、不阻塞输入。
3. 纠错**只在高置信时介入**，低置信以"提示/次选"呈现，**永不无声覆盖**人名、专名、用户刻意输入。
4. 每次纠错/改写都可**一键撤销**，并能"记住此类不再改"。
5. 整句译文有**独立、不干扰候选**的呈现方式，触发方式明确、可关闭。
6. 安装包与常驻内存**显著小于**商业"全家桶"输入法【目标待量化】。
7. 无任何广告、弹窗、推荐、捆绑；设置项克制易懂。
8. 在常见应用（系统、浏览器、Office、Electron、商店应用）中行为一致、不崩溃。
9. 开源合规：许可证清晰、来源可溯、品牌独立。

**权衡 / 主动牺牲**：
- 为**隐私与轻量**，牺牲"云端大模型带来的最高准确率"，改用"端侧为主 + 用户可选云"；
- 为**不帮倒忙**，宁让纠错**更保守**（可能少改），也不激进误改；
- 初期**只做 Windows**，牺牲跨平台的同步铺开，换取单平台做深。

## 6. 两大核心能力：技术可行性与方案

### 6.1 整句翻译

#### 路线对比

| 路线 | 质量 | 离线/隐私 | 体积/延迟 | 工程量 | 结论 |
|---|---|---|---|---|---|
| 云端翻译 API / 大模型（DeepL、混元、OpenAI、本地 Ollama 等） | 高 | 需联网、内容出端（仅用户主动开启） | 端侧几乎零增量、延迟主要看网络 | 低，**可复用青简云联想通道** | 质量首选，作为"可选增强" |
| 端侧 NMT（Argos / NLLB 蒸馏 + CTranslate2 量化） | 中（草稿级） | 完全离线 | 模型百 MB 级；CPU 推理有延迟 | 中，需 FFI 接入与模型分发 | 作为"离线兜底" |
| 纯规则/词库拼接 | 低 | 离线 | 小 | — | 不满足整句质量，放弃 |

**推荐：混合路线**——端侧轻量模型保证离线"能出译文"，用户可选开启云端获得高质量译文；默认不联网。

#### 现成轮子与真实数据点

- **Argos Translate**：基于 OpenNMT 的 **CTranslate2**；模型包 `.argosmodel`（含 CTranslate2 模型 + SentencePiece + Stanza）；语言对**平均约 100MB/对**。
- 一份本地 CPU 翻译论文（英德方向）给出的对比：**Argos 默认模型 87MB、BLEU 34.9；translateLocally 15MB、BLEU 41.8；OPUS CAT 275MB、BLEU 40.8**。
  > ⚠️ 口径提示：以上 BLEU 为**英德、特定测试集**结果，**中英方向不可直接套用**，仅说明"小模型可达可用水平"；中英质量必须自行实测。
- **NLLB-200 蒸馏 600M**：质量/速度平衡，常被推荐为起点；用 **CTranslate2** 转换并量化，官方资料称相对 PyTorch 可获 **2–5 倍加速**；CTranslate2 支持权重量化、层融合，覆盖 CPU/GPU。

#### 难点

1. **质量 vs 隐私的根本张力**：高质量整句几乎必须上云，与离线卖点冲突 → 用"可选云 + 端侧兜底"化解；
2. **端侧体积与延迟**：百 MB 模型、CPU 整句推理（数百 ms~数秒【测算】）与输入法毫秒级常驻矛盾 → 量化（INT8/INT4）、**懒加载/后台预热**、按语言包**按需下载**、仅在用户"停顿/触发"时翻译，而非逐键；
3. **交互**：整句译文不适合塞进候选词旁 → 设**独立译文区/快捷键**（如选中或停顿后弹出，可复制/替换），并提供"输入即译"开关。

### 6.2 意图匹配 / 手误纠错

#### 能力分层

```
按键/拼音串
 → ① 拼音级纠错：编辑距离 + 模糊音 + QWERTY 相邻键错按权重
 → ② 切分与候选生成：字/词候选、整句切分
 → ③ 排序与意图推断：n-gram + 神经语言模型 + 上下文 + 个人词频
 → ④ 呈现与反馈：高置信直改 / 低置信提示 / 可撤销 / 可记住
```

#### 算法与现成轮子

- **编辑距离**：经典容错输入研究（CHIME, IJCAI-11《Error-Tolerant Chinese Pinyin Input Method》）将打字错误归为**插入、删除、替换、换位**四类，用编辑距离度量拼音相似度——学术与工程依据成熟。
- **模糊音**：Rime 通过输入方案的 `speller/algebra`，用 `derive/A/B/` 为词典拼音**派生可输入编码**（如 zh↔z、ch↔c、sh↔s、n↔l、前后鼻音），是"在词典侧容错"而非"直接改用户输入"。
- **手误纠错码表（可直接参考）**：开源 `rime-cloverpinyin`（四叶草拼音）内置"智能纠错"规则，例如：
  - `derive/ao$/oa/`（oa 视为 ao）
  - `derive/([iu])a(o|ng?)$/a$1$2/`（aio=iao、aing=iang、aung=uang）
  - `derive/([aeiou])ng$/$1gn/`（gn=ng）、`derive/un$/uen/`、`derive/ui$/uei/` 等。
- **语言模型重排**：oh-my-rime 提供 grammar/搭配（collocation）惩罚等配置；青简已有 n-gram + 神经整句模型 + user 学习，可在此增强。

#### 真正的天花板：数据

- 搜狗/微软的纠错与整句能力，依托**亿万级真实输入日志 + 云端算力 + 数据飞轮**；个人/小团队难以获得同分布、同规模语料，在罕见手误、个性化表达、网络新词上天然吃亏。
- **纠错的"度"**：过度纠错会误改人名/专名，召回与精确的平衡需长期反馈调优，无法一次性解决。海外键盘评测同样指出"**自动纠错缺少舒适中间档**"是全行业通病。

#### 可务实追赶的手段

1. 直接吸收成熟**模糊音与手误规则**（Rime algebra、四叶草码表）；
2. **合成错误数据**：用公开中文语料，按键盘相邻键、常见拼音混淆，批量自动生成"错误拼音→正确"训练对，缓解真实日志缺失；
3. 更强的**量化端侧语言模型**与**个性化学习**（青简 user-* 机制是现成底座）；
4. **云端大模型兜底**（用户可选，复用云联想通道）；
5. 用**保守策略 + 提示位**替代"激进直改"，把 P3（纠错中间档）做成卖点而非短板。

#### 难点

1. 数据规模与同分布语料获取（最高难度）；
2. 纠错阈值与边界（专名/人名/俚语保护、置信度校准）；
3. 端侧模型体积/延迟与常驻约束；
4. 个性化冷启动体验与隐私的平衡（学习数据留在本地）。

## 7. 工程地基与技术栈

### 7.1 Windows TSF 要点与坑【事实】

- 现代 Windows IME **必须用 TSF** 实现，旧 **IMM32 已被系统阻止**；TSF 基于 **COM**，应用启动时为当前 IME 加载 DLL，IME 与应用处于相同应用容器（安全约束）。
- 注册经 `ITfInputProcessorProfiles::Register`；微软建议对二进制进行**数字签名**。
- **已知坑（官方问答印证）**：重启/新会话后可能出现 `ActivateProfile` 返回 S_OK、但 `GetActiveLanguageProfile` 返回 S_FALSE、DLL 未加载进新记事本的情况——即"**新装 TIP 在当前会话不完全生效，通常需注销重登/重启**"。本项目安装引导要把"重新登录后生效"写明。

### 7.2 技术栈建议（优先复用，避免重造）

| 层 | 建议 | 说明 |
|---|---|---|
| 主语言 | **Rust**（延续青简） | 生态契合、常驻安全、性能好 |
| Windows 系统绑定 | **`windows` / `windows-sys` crate**（微软维护） | TSF 为 COM，需 unsafe FFI |
| 端侧推理 | **CTranslate2（C++ 库，经 FFI/bindgen）** 或 candle / ggml(llama.cpp) | 量化、CPU 推理成熟 |
| 翻译 | 云端：复用青简**云联想通道**；端侧：**Argos / NLLB 蒸馏**量化模型 | 混合路线 |
| 架构 | 沿用"**server 进程 + TSF DLL + 命名管道 IPC**" | 系统集成与模型/UI 解耦 |
| 模型策略 | INT8/INT4 量化、懒加载、后台预热、语言包按需下载 | 控制体积与延迟 |

### 7.3 路径选择：fork 增量 vs 全新架构

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **Fork 青简做增量** | 直接获得最难的系统集成与管线，见效快、风险低 | 需吃透其代码；受 GPL 约束（本就开源，无问题） | **推荐起步方式** |
| 借鉴青简/Rime 思路重写"核心引擎"，复用其前端经验 | 架构最干净、可彻底按己意设计 | 工作量大、周期长、重复踩坑 | 原型验证、确认差异化后再评估 |

> 建议：**先 fork 做增量 + 最小原型验证**；当且仅当验证出明确差异化、且青简架构确实成为约束时，再考虑独立引擎。

## 8. 产品经理综合判断

### 8.1 分维度可行性评级

| 维度 | 评级 | 说明 |
|---|---|---|
| 基础输入与系统集成（TSF） | 高 | 青简已趟平，复用即可 |
| 整句翻译 · 云端 | 高 | 可复用云联想通道，1–2 周可出 demo【测算】 |
| 整句翻译 · 端侧 | 中 | 可行，质量/体积/延迟需实测 |
| 纠错 · 规则/模糊音级 | 高 | 成熟规则与开源码表可直接吸收 |
| 纠错 · 对标商业大模型 | 低–中 | 受数据规模限制，难全面对标 |
| 隐私/无广告差异化 | 高 | 市场空白明确、有成功样本（FUTO 等） |
| 个人/小团队可持续维护 | 中–低 | 需长期投入，应控制范围 |

**总体结论：项目可行，但应"窄切口、深打磨、快验证"。** 不要以"超越搜狗的全能输入法"为目标，而以"**隐私可信 + 纠错有分寸 + 能翻整句**"的差异化产品立足。

### 8.2 核心难点排序

1. **数据规模/同分布语料**（决定纠错与整句上限）；
2. **端侧模型的质量—体积—延迟平衡**；
3. **纠错阈值与边界**（不帮倒忙、赢得信任）；
4. **跨应用 TSF 兼容与签名/安装体验**；
5. **长期维护精力与开源合规**。

### 8.3 亮点 / 差异化机会

1. **默认离线 + 零广告 + 轻量**，切中 P1/P2/P6，且有 FUTO、青简验证过的需求；
2. **"恰到好处"的纠错中间档**（保守直改 + 提示位 + 可撤销 + 可记住），直击行业通病 P3，最具记忆点；
3. **整句翻译的混合路线**（端侧兜底、云端可选、用户可控），把青简的"译词"自然进化为"译句"；
4. **站在巨人肩膀**：青简的集成、Rime 的规则、Mozc 的工程，避免重复造轮子；
5. **开源 GPL 回馈与致敬**，利于吸引早期贡献者与信任型用户。

### 8.4 优化点（相对青简，落到需求）

| 方面 | 现状 | 优化方向 |
|---|---|---|
| 翻译 | 单词/词组译词 | 整句翻译 + 独立译文面板/快捷键 |
| 纠错 | 较弱 | 模糊音、相邻键、编辑距离、整句意图、个性化 |
| 交互 | 译词依附候选 | 整句译文独立区、设置可视化、撤销/记住 |
| 性能体积 | 已有本地模型 | 量化、懒加载、按需语言包 |
| 兼融各家 | — | 搜狗的整句/云兜底、微软的稳定安静、Rime 的可定制、FUTO 的隐私 |

### 8.5 SWOT 简表

| | 有利 | 不利 |
|---|---|---|
| **内部** | **S**：复用青简成熟地基；差异化清晰（隐私+纠错分寸+整句）；开源 | **W**：数据少、端侧模型受限、个人精力有限、品牌新 |
| **外部** | **O**：隐私意识上升；商业输入法广告臃肿引发逃离；开源/端侧模型成熟 | **T**：商业大厂 AI 能力强且免费；系统输入法预装；分发与签名门槛 |

## 11. 许可证与合规

1. **GPL-3.0-or-later 传染性**：基于青简的衍生作品须以同等许可证**开源**（对开源致敬项目可行）；需保留版权与许可声明。
2. **品牌独立**：青简的**项目名与 logo 不在授权内**——必须使用自有名称（如"灰迹"）与图标，可在文档/关于中注明"基于并致敬青简"，但不冒用其名号。
3. **数据许可**：青简随包词库、语言模型、译词数据**各有许可**，分发前逐项核对；自行新增的语料与模型同样要确认可再分发。
4. **签名与安全**：Windows 二进制建议数字签名，否则会触发 SmartScreen；安装引导说明"注销重登后生效"。
5. **隐私承诺一致性**：默认离线、最小化收集；任何云端功能默认关闭、显式告知、可随时撤回。
