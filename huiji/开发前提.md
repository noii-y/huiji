# 灰迹输入法 · 开发前提

> 立项前的事实底稿与产品判断，用来统一“做什么、能不能做、难在哪、先做什么”。
>
> 口径：**【事实】**可查证、能直接引用；**【测算】**是推断，落地前要实测；**【待验证】**方向成立，但关键指标还没拿到。文档日期 2026-10-03。

---

## 1. 背景与定位

### 缘起

用了开源拼音输入法**青简（qingjian）**，认可它本地优先、重隐私、候选词旁带学习译词，但有两处明显不够：

1. 只译单词词组，打出整句时给不出整句译文；
2. 拼错、漏字母、按错相邻键时，猜用户本意的能力偏弱。

想以青简为**基石**、向它致敬，再糅合搜狗、微软拼音的长处，做一款新输入法，工作名**「灰迹」**。

### 一句话定位

隐私优先、离线可用、无广告、轻量的拼音输入法，在青简“译词”之上，提供**整句翻译**和**有分寸的手误纠错**。

### 关键判断

- 最难的系统集成（Windows TSF、候选渲染、模型管线、跨平台）青简已经趟平，该站在它肩膀上做增量，不从零重写。
- 整句翻译主要是路线选择和工程优化，可行性较高。
- 纠错算法成熟、能改进，但天花板取决于训练数据规模——这是和搜狗、微软差距最大、最难补的地方。
- 市场有空位：**隐私 + 无广告 + “纠错有中间档”**，比再做个大而全的输入法更现实。

---

## 2. 基石：青简【事实】

- Rust 编写，**GPL-3.0-or-later**，项目很新（2026-09 起步），支持 macOS / Windows / Linux。
- 架构是“后台服务进程 + 各平台输入法前端 + 本地数据”：Windows 前端是 TSF（COM DLL），和后台通过命名管道通信，不走网络端口。
- 本地有词库、语言模型、领域词库，还有一个给拼音串重排候选的神经模型（是语言模型，不是翻译模型）。
- 自带云联想通道，**默认关闭**，用户可自填 AI 服务商、请求不经过青简服务器——这是后续做云端翻译和兜底纠错能直接复用的路。

能力边界：本地拼音转字词整句、候选旁译词、n-gram 加神经重排、个人词频学习、中英切换都有；没有整句翻译，纠错和 Windows 兼容性偏弱——正是本项目的机会点。

---

## 3. 市场与竞品

商业输入法整体在转向“词库为基础、生成为核心”。搜狗 2026 年全面 AI 化，整句、翻译、意图都靠大模型，但广告、弹窗、臃肿也最被诟病；微软拼音胜在系统级稳定、安静、无广告，云能力克制。搜狗云输入有个交互值得学：特定条件下把计算放到服务器，云端结果放**第二个候选位**，长句比本地准。

开源这边，**Rime（中州韵）**高度可定制、靠输入方案给词典派生容错编码，**Mozc**（Google 日语）转换工程成熟，但它们本质是引擎、不带现成方案，要自己折腾。这些成熟项目都采用“核心引擎和平台前端分离”，和青简一致，印证了沿用这套架构是对的。

校准产品品味时，除了中文输入法，还放了两个类别外的参照：**FUTO 键盘**（离线、反追踪，靠信任做成了生意）和 **CleverType / Argos**（离线翻译的落地形态），免得只盯着中文造成局部最优。

## 4. 用户与痛点

**初期用户**：看重隐私、烦广告弹窗、不想要臃肿输入法的人；有外语学习或跨语言沟通需求、想边打边看的人；对准确性和性能敏感的开发者、写作者；愿意试早期开源产品的技术爱好者。

**核心 Job**：在任何应用里打字，都能又快又准、不被打扰、不被监视地把想法变成文字；拼错或要跨语言时，恰到好处帮一把，而不是帮倒忙。

痛点与对应：

- **隐私焦虑**（键盘看得到密码私信、切购物 App 后出相关推荐）→ 默认离线、数据不出端。
- **广告臃肿** → 零广告、单一职责、轻量。
- **纠错没有中间档**（要么激进误改专名人名，要么全关）→ 核心差异化：保守可控的纠错加一键提示。
- **首选不准**（常用词被挤后面）→ 更强意图模型加个性化学习。
- **翻译割裂**（有单词译词、整句还得切 App）→ 整句翻译，端侧兜底加云端可选。

## 5. 产品定义

**价值主张**：默认离线、零广告、数据归用户；纠错有边界、可回退；从译词进化到译句、离线兜底云端可选；常驻低占用、响应即时。

**功能分档**：

- **MVP**：继承青简拼音与译词，整句翻译最小闭环，保守可控的手误纠错，基础设置与品牌替换，只做 Windows。
- **增强**：个性化学习、更强端侧模型、译文独立面板、主题皮肤、更多语言对、云端兜底。
- **非目标**：广告、内容商城、无关全家桶、默认上传、强制账号。

**“好”的硬标准**：断网也能完成拼音转汉字和基础译词；按键到候选保持即时、重模型不阻塞输入；纠错只在高置信介入、永不无声覆盖专名人名；每次改写能一键撤销、能“记住这类不再改”；常见应用里行为一致不崩溃；许可证清晰、来源可溯。

**主动牺牲**：为隐私和轻量，不上云端大模型的最高准确率，改端侧为主、云端可选；为不帮倒忙，纠错宁保守；初期只做 Windows，换单平台做深。

## 6. 两大核心能力

### 6.1 整句翻译

三条路：**云端 API** 质量高、但要联网且内容出端，端侧零增量、工程量低，作为可选增强；**端侧神经翻译**（NLLB 蒸馏等，量化后模型百 MB 级）完全离线、质量是草稿级，作为离线兜底；纯规则拼接质量不够，放弃。

推荐**混合**：端侧保证离线能出译文，云端可选求高质量，默认不联网。

难点：高质量几乎必须上云、和离线卖点冲突，用“可选云加端侧兜底”化解；百 MB 模型加 CPU 推理，和输入法毫秒级常驻有矛盾，靠量化、懒加载、按需下载、只在停顿时译；整句译文不适合塞候选旁，要有独立呈现和快捷键。

### 6.2 意图纠错

分四层：拼音级（编辑距离、模糊音、相邻键权重）→ 切分生成候选 → 排序推断（语言模型、上下文、个人词频）→ 呈现（高置信直改、低置信提示、可撤销）。编辑距离容错和模糊音派生都有成熟的学术与开源依据，Rime 的输入方案和四叶草拼音的纠错码表能直接吸收，不用从零想。

**真正的天花板是数据**：商业输入法靠亿万级真实日志、云端算力和数据飞轮，小团队拿不到同分布语料，在罕见手误、个性化表达、网络新词上天然吃亏；纠错的“度”要长期调，没法一次到位。

可务实追赶：直接吸收成熟模糊音和手误规则；用公开语料按相邻键和常见混淆批量合成错误对；强化端侧模型和本地个性化学习；云端大模型可选兜底；用保守策略加提示位，把“纠错中间档”做成卖点。

## 7. 工程地基

现代 Windows 输入法必须挂 TSF（旧 IMM32 已被系统阻止），基于 COM，建议数字签名；新装的输入法在当前会话可能不完全生效，通常要注销重登，安装引导要写明。

技术栈延续 Rust 和 windows crate，端侧推理用 CTranslate2 之类的成熟引擎，整体沿用“server 进程 + TSF DLL + 命名管道”，新增能力做成独立模块。

路径上，**fork 青简做增量**能直接拿到最难的系统集成、见效快风险低，是推荐起步；只在验证出明确差异化、且青简架构确实成约束时，才考虑独立引擎。

## 8. 产品经理判断

**可行性**：基础输入和系统集成高（复用即可）；云端翻译高；端侧翻译中；规则级纠错高；对标商业大模型的纠错低到中（受数据限制）；隐私无广告差异化高；个人长期可持续维护中到低。

总体：项目可行，但要**窄切口、深打磨、快验证**，别以“超越搜狗的全能输入法”为目标。

**难点排序**：数据规模；端侧模型质量—体积—延迟的平衡；纠错阈值与边界；跨应用兼容和签名安装；长期精力与开源合规。

**亮点**：默认离线、零广告、轻量；“恰到好处”的纠错中间档最有记忆点；整句翻译混合路线把译词自然进化成译句；站在青简、Rime、Mozc 肩膀上不重复造轮子；GPL 开源回馈致敬。

**SWOT**：优势是地基成熟、差异化清晰、开源；劣势是数据少、模型受限、精力有限、品牌新；机会是隐私意识上升、商业输入法臃肿引发逃离、端侧模型成熟；威胁是大厂 AI 强且免费、系统输入法预装、分发签名有门槛。

## 9. 许可与合规

GPL 有传染性，衍生作品须同等开源、保留版权声明，对开源致敬项目没问题。青简的项目名和 logo **不在授权内**，必须用自有名称图标，可在致谢里注明基于青简。随包词库、模型、译词各有许可，分发前逐项核对。Windows 二进制不签名会触发 SmartScreen，安装引导要说明。
