- **两个 cargo 命令同时跑会争 target 目录的锁**，后启动的那个会一直 Blocking waiting。以后同一时刻只跑一个编译任务。
- Windows 上编译 server 要设 `QINGJIAN_UIACCESS=0`。它的 build.rs 默认往 exe 里嵌 uiAccess 清单，没签名的测试程序带着这个清单起不来（os error 740）。

## 2026-10-03 · 阶段 2B（一）：先把纠错的尺子立起来

### 为什么没直接改纠错

原打算拿阶段 1 的 replay 当纠错基线，跑的时候发现它会冤枉引擎：日志里 `byong` 两条记录当时首选就是「不用」（简拼 b+yong 直接命中），但 replay 从头冷重放到这儿，却报「用 / 永 / 勇，不在候选」。

挖下去是这么回事：replay 用冷引擎按顺序重放，内存里学出来的上下文跟真实当时不一样，到 `byong` 触发了引擎的过度纠错——把首字母 b 当错字删掉、切成 yong。这把 replay 的基线拉低了，也顺带暴露了一个真实的误纠倾向。结论是阶段 2B 不靠这种"学习路径敏感"的重放，改用 cli 的 `--eval-text`：每条独立清空、断链、不学习，状态统一，结果才可信。

### 做了什么

- 从输入日志提真实纠错：`corrected=true` 共 20 条，去重 19 条，存成《评测/手误/真实纠错.tsv》。
- 写了合成生成器 `tools/gen_typo_set.py`：从 dict.tsv 取词频 ≥40 的 2-4 字词，固定随机种子，
  按换位、漏 1 字母、多 1 字母、相邻键替换、声母缩写、模糊音六类注入，每类 160 条，外加 400 条防误纠。
- 在没动过的引擎上跑完全部对照，得到增强前基线，数字和判断写在《评测/手误/基线-手误.md》。

### 两个值得记的判断

- 青简的一处编辑纠错，在"切不干净"时已经做得不错，真实 19 条首选 89.5%，真实手误里约七成五是相邻字母敲反，"换位优先"的路子没错。
- 真正的召回缺口在"漏字母后还能切成别的合法音"：`huojiu→huoju` 切成 huo'ju 出「火炬」、`danshen→dansen` 切成 dan'sen 出「单色」，引擎看着没问题就将错就错，正确词不进候选。声母缩写反过来，召回 91%、首选 66%，是排序问题。

### 自检

| 检查项 | 结果 |
| --- | --- |
| 生成器固定种子、重复跑输出一致 | 通过 |
| 8 个 TSV 都能被 eval 读取、条数对 | 通过（19 + 6×160 + 400） |
| 基线数字可复现 | 通过，两次批量跑一致 |
| 模糊音 chha 类误形态 | 已修（声母最长匹配），复跑正常 |

踩的小坑：PowerShell 读无 BOM 的 UTF-8 日志得加 `-Encoding UTF8`，不然中文行 ConvertFrom-Json 失败被 try/catch 吞掉，20 条纠错一开始只数出 1 条；sandbox 自带的 python 跑 OneDrive 路径脚本不注入 `__file__`，改用 `sys.argv[0]` 定位。

### 下一步

做召回增强：对“切得干净、但原样首选概率不高”的输入，并行试一处编辑，把“纠错后明显更可能”的词加进候选、先不抢首选。改完同一份对照集重跑，防误纠不能跌破 98.2%。

## 阶段 2B（二）：中文优先默认开，声母缩写首选 +11

### 先撞了堵墙：干净串一处编辑召回是死路

第一版破坏了既有测试 typo_edges...（jineng 场景，期望候选里没有近藤，召回借“插入 t→jinteng”把高频近藤加了进来）。重构时复用 plain_sentence 的保护——原样任一完整切分能读出无占位词就不召回，重构后 302 测试全过。

但 release cli 重跑八个对照集，数字跟增强前逐项一致，recall 在所有集上都返回空。想明白了：切得干净的串，原样切分通常就能读出词（哪怕是更常用的别的词），保护恒成立；切不干净的走 active_correction、不经过 recall。“切得干净 AND 原样读不出词 AND 一处编辑能读出”这个触发条件，数据里基本不出现，代码撤了。

## 阶段 2A（一）：云端整句翻译探针与 100 句测试集

### 先摸清底：云端翻译通道青简已经写好了

动手前把 predict crate 翻了一遍，发现整句翻译的网络层不用新建：
- PredictionKind 有 Translate，请求带 text（原文）和 target_language，回复的 sentence 就是译文；
- CloudPredictor 在后台线程发 OpenAI 兼容请求，submit / poll 走通道，不阻塞输入；
- Engine 有 request_translation(text) 发起、poll_prediction() 取回，译文在 prediction.sentence。

青简现在的用法是“选中一段文字 + 快捷键”的划词翻译，缺的是“打整句拼音直接给译文”这条产品路径。

### 做了什么

- cli 加整句翻译探针：`--translate "句子"` 单查，`--translate-file` 批量读 TSV，逐句打印原文 / 译文 / 耗时，`--translate-save` 存结果表。
- 建了 100 句测试集（huiji/评测/翻译/测试集.tsv），分九类：日常聊天、生活出行、工作职场、情绪口语、问句、网络用语、长句、数字时间、日常琐事，尽量写成像真人会打的口语，没堆“你好谢谢”。

### 自检（不依赖网络的部分都跑了）

- 编译干净，无 warning；
- 不开云端时提示清楚：“整句翻译不可用，需要 --predict 且配置密钥”；开了 --predict 没 key 时提示去配 QINGJIAN_API_KEY；
- --translate-file 能正确解析三列 TSV，读到句子后才在第一句报不可用，说明解析没问题。

### 卡住的地方

真实翻译要一个 OpenAI 兼容的 key（配置默认就是 DeepSeek）。机器上和青简配置里都没有，这步得请你提供。拿到 key 我就把 100 句全跑一遍，出质量分和延迟中位数，再决定端侧要不要做。

## 2026-10-03 · 阶段 3（一）：端侧推理进 Rust，Ruy 链路端到端打通

### 选型：ct2rs，而不是 candle 或 onnxruntime

Python 探针用的是 CTranslate2，进 Rust 前我把几条路都过了一遍：

- **ct2rs**：CTranslate2 生态的 Rust 绑定（cxx，内存安全），高层 `Translator` 把分词、生成、解码全包好，明确测过 Marian-MT。等于直接复用探针验证过的那套 C++ 内核，模型一个字节都不用转。
- candle：纯 Rust、没有 C++ 依赖，但 CPU 算子优化弱，还得把 Marian 模型转成它的格式，等于重写一条没验证过的链路。
- ort（onnxruntime）：要先把模型转 ONNX、再手写生成循环，灵活但活儿多。

最后选 ct2rs，重依赖用 feature 隔离，默认编译不被它拖慢。上层还有个叫 trad 的 crate 更省事，但太新（0.1）、自动下载 NLLB、黑盒，没敢用。

### 独立探针踩了三个坑

正式接入前，在 workspace 外搭了个一次性探针，把 Windows 上的坑先趟完：

1. **CRT 对不上**。ct2rs 编译 CTranslate2 默认静态 CRT（/MT），Rust 默认动态 CRT（/MD），头一回链接报一堆 LNK2038、LNK2005。构建加 `RUSTFLAGS=-C target-feature=+crt-static`，两边都静态 CRT 就过了。
2. **分词器自动识别失败**。`Translator::new` 会自动猜分词器，没认出 source.spm / target.spm。改用 `with_tokenizer`，显式喂 SentencePiece。
3. **中文路径打不开**。模型放在 OneDrive 的“灰迹输入法”目录，SentencePiece 底层按系统代码页（GBK）解释路径，报 Not found，复制到纯英文路径立刻跑通。**正式安装目录必须保持英文**，比如 %LOCALAPPDATA%\Huiji。

探针性能：Ruy 后端、8 线程，固定 5 句延迟中位数 749ms，摸到了 800 的边。

### 正式接入

- qingjian-predict 加 `LocalTranslator`（实现 `Predictor`），和 CloudPredictor 同一个套路：后台线程加通道，推理不阻塞输入。ct2rs 用 `local-nmt` feature 隔离，默认 Ruy、int8。
- cli 加 `--local-nmt <模型目录>`，给了就离线翻译、不碰云端；`--translate`、`--translate-file` 原样复用，单句和批量都通。

### 100 句实测：质量更好，延迟没达标

cli 批量跑完 100 句，逐句打了分（端侧-ruy-评分.tsv）：

- **质量**：84 句 ≥3（84%）、均值 3.78，重复退化只有 1 句。比 Python 那版（88% ≥3、均值 3.53、多句残留重复）还干净，重复抑制在 Rust 这条链路真正生效了。
- **延迟**：中位数 **956ms**、均值 1010、P90 1410，只有 24% 的句子在 800ms 以内。**这条没达到自定的 800 门槛**，如实记下。

探针 standalone 是 749ms，进真实批量变成 956，差距主要在句长——探针只测 5 句短句，100 句里长句、复杂句多，解码步数上去就慢；通道往返只占零头。

### 判断和下一步

- 质量达标、还略好；延迟是明确短板。整句翻译是异步的，译文出现在打完一句的停顿间隙、不卡打字，956ms 体感几乎无感，但标准定了 800，没到就是没到，不拿体感给自己开脱。
- 满血后端有现成轮子：ct2rs 的 `mkl` feature 基于 `intel-onemkl-prebuild`，cargo 自动拉预编译 MKL，不用手动装几个 G 的 oneAPI。Python wheel 用 MKL 是 83ms，下一步就验证它在本机（AMD Zen4）编不编得过、能快多少、体积多大。
- 安装目录英文是硬约束，品牌化阶段一并处理。

## 2026-10-03 · 阶段 3（二）：复用预编译内核，延迟降到 50ms

### MKL 在 Windows 是条断头路

照着上一步的打算，先验证 ct2rs 的 `mkl` feature。开头就卡住：intel-onemkl-prebuild 在 Windows 上靠 `nuget.exe` 装静态 MKL，机器里没有这个程序，build 脚本直接 panic。去官网下了个 nuget.exe 放进 cargo bin，才把依赖编过去。

编是编过了，运行连错两次：

- int8：`the target device or backend do not support efficient int8 computation`。
- 换成 float32：`No SGEMM backend on CPU`。

读到这里就明白了。之前 MKL 和 Ruy 一起开着能跑出结果、延迟却跟纯 Ruy 一模一样，是因为 int8 的活儿一直是 Ruy 在干，MKL 压根没接上。静态链接那套 MKL，CTranslate2 运行时根本没认出来。`mkl` feature 我没删，留着备查，正式链路不走它。

### 真正让 Python 快的是 oneDNN，而它已经在 DLL 里

回头看 Python wheel：一个 56.5MB 的 ctranslate2.dll，里面打包的是 oneDNN，不是 MKL。CTranslate2 在 x86 CPU 上的高效 int8 路径本来就走 oneDNN，oneDNN 是开源的，对 AMD 的 AVX2/AVX-512 一视同仁，也没有 MKL 那种给对手 CPU 降速的毛病。

ct2rs 确实有 `dnnl` feature，但那是从源码编译完整 oneDNN，默认还编训练算子，Windows 上一趟二三十分钟，OpenMP 链接也得自己收拾。我不想等这个。

更省事的办法摆在眼前：Python wheel 里那个 dll 是现成的、满血的，版本号 4.8.2，跟 ct2rs 0.10.1 内嵌的 CTranslate2 完全一致，头文件和 ABI 对得上。直接链接这个 dll，一行 C++ 都不用编。

### 怎么接的

- SDK 放纯英文路径 `%LOCALAPPDATA%\HuijiSDK\ct2`（中文路径的坑上一步踩过）。bin 里放 ctranslate2.dll 和 libiomp5md.dll（OpenMP 运行时，cudnn 那个是 GPU 用的，不带）。
- `dumpbin /exports` 倒出 13204 个符号，写成 .def，再用 `lib /def` 生成 ctranslate2.lib 导入库。
- ct2rs 的 system 分支在 Windows 上有点离谱：明明是纯 CPU，它也硬要链接 cpu_features、cublas、cublasLt，少一个都报错。桥接层并不真调这些，我做了几个空占位库应付链接器。
- 新增 `local-nmt-system` feature，用动态 CRT 匹配 dll，构建时只编 cxx 薄桥接。

### 结果（数字）

100 句 cli 批量跑完：

- **延迟中位数 50ms**、均值 65.7、P90 101，最快 50、最慢 101。100 句全部在 800ms 以内，实际没有一句超过 101。
- 空译文 0，重复退化还是只有 #55 那一句。
- cli 可执行文件 13.47MB。

对照 Ruy 的 956ms，快了十九倍，800ms 这条门槛算是大幅跨过去了。

质量没有重新逐句打分。模型和生成参数都没动，换后端只带来数值上的微小差别：33 句译文跟 Ruy 版不一样，逐一看过去基本是等价改写，单复数、时态、措辞的区别，其中不少反而更顺——「高铁」Ruy 只译出 high-speed，oneDNN 给全了 high-speed train；「破防」Ruy 译成 breaking up the family，oneDNN 是 It's really moving。质量在同一个档，重打一遍分改变不了结论，就不做这个样子活了。

### 判断

- 端侧离线翻译这条线到这儿立住了：免费、离线、数据不出本机，中位数 50ms。当初担心的「本地推理慢」，靠复用现成 dll 绕过去了，没在编译内核上耗时间。
- 这个选择还有个长尾好处：以后改 Rust 代码，链接的是现成 dll，几秒出包，不用每次陪着 C++ 编译。
- 分发要多带两个 dll，加起来约 61MB，对输入法不算负担。许可上 CTranslate2 是 MIT、oneDNN 是 Apache-2.0、iomp 是 Intel 的再分发条款，品牌化打包时逐项核对一遍。
- #55「摸鱼」误译还带着重复，是仅剩的明显退化。流行语、专名、数字这几块的短板，后面用本地术语表兜底（高铁→high-speed rail、摸鱼→slack off）。

### 下一步

打整句拼音直接给译文的 Compose 路径（现在译文只能靠选中文字触发，产品路径还没接上），然后进入品牌化 P0：名称、图标、设置页、英文安装目录。

## 2026-10-03 · 阶段 3-d：打整句拼音，直接给整句英文译文

### 骨架本来就在，只差翻译器肯接

读 Engine 的预测代码时发现，组句中发请求这条路径早就铺好了：每次查询候选之后，Core 会顺手发一个 Compose 请求，里面带着 `guess`——本地整句转换组出来的中文句子。云端那套 CloudPredictor 收到后返回的是中文整句补全，cli 里对应 `☁ 整句:` 那一行。

也就是说，打整句拼音 → 拿到一个整句结果，这条链路不缺，缺的只是让端侧翻译器在 Compose 时也开口。

### 改动很小

只动了 LocalTranslator 的 `submit`：

- Translate（选中文字翻译）：原文取 `text`，和以前一样。
- Compose（打整句拼音）：原文取 `guess`，把本地组好的中文喂给模型。
- Question（问字）：不翻译，直接跳过。

后台线程一个字没改，它只管把收到的中文译成英文，不关心这中文是选中的还是拼音组的。

### 验证

cli 里直接敲连续拼音，不选词、不选中：

- `nijintianwanshangyoukongma` → Are you free tonight?
- `woxiangdianyubeinaicha` → I'd like to order some milk tea.
- `jintiantianqizhenbucuo` → It's a nice day.

三句都一次给对。单元测试补了 Compose 用 guess、guess 为空、Question 忽略三种情况，predict 一共 21 个测试全过，system clippy 也干净。

### 一个留到 UI 阶段的点

Core 现在把 Compose 回来的 `sentence` 一律当「整句补全」处理，真机上按 Tab 会把这句上屏。云端时代 sentence 是中文，这么干没问题；现在 sentence 是英文译文，用户在打中文，Tab 却上英文，就不对了。

译文更合适的位置是候选窗里的一行参考，跟青简在词旁边标译词一个思路：看得到、但不抢正常选词、Tab 不会误上。这要在 Prediction 上标一句「这是译文」，再让 Windows 候选窗按参考行渲染，属于界面的活，放到下一步，先把数据链路走通的决定记在这里。

### 小结

到这一步，当初定的两件事——整句翻译、打整句拼音直接给结果——逻辑和数据链路都通了，而且全程离线、中位数 50ms、数据不出本机。剩下的是把译文在真实候选窗里摆对位置，以及品牌化。

## 2026-10-03 · 阶段 3（真机）：端侧翻译接入 Windows server，候选窗给整句译文

### server 这边，渲染的活早就齐了

3-d 在 cli 里把「打整句拼音给译文」跑通，但 cli 不是用户真正打字的地方。这一步要把端侧翻译塞进 Windows 的 server 进程，就是后台常驻、被 TSF DLL 连的那个。

读 server 代码发现，显示整句结果的机制它本来就有：组句时 server 发预测请求，结果回来把 `prediction.sentence` 存下，帧里带上 `sentence` 字段，候选窗照画。云端的中文整句补全走的就是这条道。真正缺的只有两件事：让 server 能挂端侧翻译器（原来只挂云端），以及 Tab 别把英文译文当补全上屏。

### 改了什么

- server 加三个端侧 feature（`local-nmt` / `-mkl` / `-system`），透传到 predict，默认推荐 system。
- 启动时多走一步 `attach_local_translator`：在用户目录和随包目录找 `models/opus-mt-zh-en-ct2`（目录里要有 model.bin），找到就挂 LocalTranslator、覆盖云端那套。端侧优先，离线，不依赖 key。
- Router 加一个 `local_translation` 标志，挂上端侧翻译器时置 true。
- Tab 逻辑分叉：端侧模式下 sentence 是英文译文，Tab 照常翻候选页、不接受这句；云端模式维持原样，有中文补全就 Tab 上屏。

### 部署时被文件锁绊了一下

往 D:\Qingjian 替换 server，第一次直接复制，报「文件正由另一进程使用」。server 是 TSF DLL 按需拉起的，停掉它，DLL 很快又拉起一个，文件一直被占。

Windows 允许重命名一个正在运行的 exe，只是不让删。于是先把旧 server 改名成 `qingjian-server.old.exe`，再把新 exe 放到原位，最后停掉持有旧文件的进程，DLL 重新拉起时用的就是新的了。原始 0.1.4 的 server 另外备份成 `qingjian-server.exe.orig.bak`，回滚改名换回来即可。

### 真机验证（系统记事本）

真实词库 92825 条、语言模型 13.9 万词正常加载，server 日志确认「端侧整句翻译已接入（离线）」，管道监听、DLL 连上。

记事本里连续打 `nijintianwanshangyoukongma`，不选词：

- 候选窗顶部、拼音行右侧直接给出整句英文 **Are you free tonight?**，翻译准确。
- 候选词旁边原有的单词译词（you / girl / intend 这些）照旧，两套共存。
- 按 Tab，页码 1/4 翻到 2/4，记事本正文没有出现任何英文字母。

3-d 留到「UI 阶段」的点，这一步一并解决，没动 Core 的 Prediction。平台层 Router 自己按标志决定 sentence 怎么显示、Tab 怎么处理，Core 不用知道这句是译文还是补全。

### 自检

- system feature：clippy 无告警，server 真机进程内 LocalTranslator 加载成功。
- 默认 feature（提交钩子查的就是它）：clippy 干净；端侧相关函数都加了 cfg 门，不编翻译时不会留下「never used」。
- cargo fmt 已过。

### 还没做

- 云端整句翻译仍缺 OpenAI 兼容 key，链路代码就绪，拿到 key 就能出云端对照。
- 网络流行语、专名、数字这些质量短板没动，下一步是本地术语表兜底。
- 品牌化（名称、图标、设置页、安装目录 ASCII、打包带上两个 dll 和模型）还没开始。

### 下一步

端到端在真机走通，灰迹已经能在日常打字时给整句译文。接下来按计划做品牌化 P0，把这套东西打成一个有自己名字、能独立安装的包。

### 先看清端侧模型到底栽在哪

三分糖、三千二这类是数字和量词的问题，跟术语不是一回事。

### 源端替换被探针证伪

一开始想在翻译前把中文术语换成标准英文（摸鱼→slack off），让模型照着组句。探针（tools/term_probe.py）结果不理想：模型会把塞进去的英文短语拆碎再变形，slack off 变成 ex-srack off，high-speed rail 变成 gh-speed Rail，没见过的占位符也保不住。只有 overwhelmed 这种单个常见词偶尔能透传。这条路会把原本通顺的句子搞坏，放弃。

### 改成译文后处理，规则刻意收得很窄

在模型译好的英文上做替换，只动两类短语：正常英语几乎不会出现、模型又稳定这么译的。摸鱼的 feel/touch the fish 按时态人称还原成 slack off / slacks off / slacking off / slacked off；内卷的 inner volume 换成 rat race。代码在 crates/qingjian-predict/src/terminology.rs，在 LocalTranslator 产出译文时过一遍。

复现、神仙颜值、破防这些模型每次译法都不一样，没法用固定模式安全替换，就没硬救——硬加规则更容易误伤。数字组合也不在这一层解决。

## 阶段 3-i：游戏模式——全屏时输入法让位，顺手修了候选窗不显示

你一次报了两件事：日常打字能打、但候选框不出来；玩三角洲行动全屏直接卡死，能 Alt+Tab。两件事分开处理。

### 先看候选窗为什么不显示

查下来 server 进程活着、线程都在正常等待、日志没有报错，但枚举顶层窗口——这个进程一个窗口都没有。候选框不是被隐藏或挪到屏外，是窗口压根没建出来。

再看 TSF 端日志，对得上：你打字的时候 server 明明回了 9 个候选、键也被消费，数据链路是通的，唯独窗口没显示。时间点卡在 23:10——那一阵有多个 server 实例启动、命名管道反复重连，日志里一片「管道被占」「管道正在被关闭」（os error 231/232）。窗口状态就在这次混乱里被弄坏了，之后没有随新输入重建。

修复很直接：杀掉 server，让 TSF 重拉一个干净实例，候选窗立刻恢复。这也记下一个健壮性隐患：候选窗窗口在管道/实例混乱后可能丢失且不自愈，目前靠重启恢复，后面应该加窗口自愈，不能让用户手动杀进程。

### 游戏卡死的根因和做法

三角洲是独占全屏、带 ACE 反作弊。这种环境下输入法做两件事都危险：TSF 在游戏 UI 线程上同步连命名管道等结果，server 再把分层候选窗盖到全屏画面上。前者卡住游戏主循环，后者会触发全屏设备抢占，合起来就是游戏卡死、但系统没死机（所以能 Alt+Tab）。

做法是给输入法加一个游戏模式：**前台一全屏，输入法整体让位——不吃键、不连 server、不弹候选窗，按键全直通游戏。** 上面两件危险的事都不会发生。

- 新增 `com/game_mode.rs`，判定前台窗口是否盖满整个显示器（带标题栏的最大化不算，任务栏自动隐藏时那种要照常输入）。检测逻辑和 server 状态条一直在用的全屏判断同源。
- 在 `OnTestKeyDown`、`OnKeyDown` 最前面拦截，全屏就直接返回 FALSE；进全屏前若有敲了一半的拼音，先落定，避免残留在文档里。
- `huiji/tools/` 下留了一个 `fullscreen_test.py`，能造一个无边框全屏窗口，以后验证这类问题不用临时找游戏。

### 自检

- `cargo clippy -p qingjian-windows-tsf` 0 warning，64 位、32 位 release DLL 都编过。
- 真机重启 Notepad++（让它加载新 DLL）走了一遍完整生命周期：窗口化打 `nihao`，候选窗照常；F11 进全屏打 `ceshi`，没有候选窗、字母直接上屏；F11 退出再打 `nihao`，候选窗恢复。
- 日常候选窗不显示的问题，重启 server 后已恢复。

### 取舍和待确认

全屏即让位，会顺带覆盖全屏看视频、全屏演示里打字的场景，不过这些场景本来就少，退出全屏即可；无边框全屏（窗口化全屏）游戏也会被判成全屏、同样让位，宁可稳一点。代价是全屏游戏里不能用灰迹选词——独占全屏加反作弊，自绘候选窗本来就会卡死，这是用「不卡死」换「全屏选词」。

三角洲独占全屏加 ACE 的极端环境，逻辑上游戏模式同样生效，但 Notepad++ 模拟不出反作弊那层，需要你实际进游戏打几个字确认。后续如果想在窗口化游戏里输中文，再加按 exe 的游戏列表、豁免名单和手动开关。

### 翻页：默认 `-`/`=`，小键盘 +/-，PageUp/PageDown

起因是你用惯了 Windows 自带输入法，想拿加减号翻页、而不是 Tab。查下来 `-=` 这档青简上游早就写好、也有测试，只是默认给的是 `[]`；Esc 清空、Enter 保留原始字母、上下移焦点、PageUp/PageDown 翻页，也都已经跟微软一致。真正要动的就两处：

- 默认翻页档从 `[]` 改成 `-=`：缺省字符常量、GeneralConfig 默认值、首次运行模板三处一起改；新增一个 `PAGE_KEYS_DEFAULT` 字符串常量跟字符常量对应，免得两处手写、改一处漏一处。
- 小键盘 `+` 补成下一页：小键盘 `-` 敲出来的字符是 `-`，本来就能匹配；小键盘 `+` 字符是 `+`、匹配不到主键盘 `=`，原来落进了缓冲区。改成在翻页解析最前先按 VK 认小键盘加减，于是任何翻页档下小键盘 `+`/`-` 都翻页。

自检：

### Ctrl+. 切换中英文标点

微软拼音里 Ctrl+. 在中文标点（，。）和英文标点（,.）之间切。灰迹本来就有全角标点开关，状态条和任务栏菜单也能点，就缺这个快捷键。标点是中英模式各记一份，状态条那段逻辑已经够用，我把它从状态条事件里抽成一个独立的 `toggle_punctuation` 方法：状态条点击调它、快捷键也调它，两条入口不会改出不一样的行为。

快捷键识别放在按键分流最前面。原来带 Ctrl 的键会在「有没有命令键」那一步直接放行给应用，所以得在那之前拦。匹配条件是句点键（VK 0xBE）加仅 Ctrl，带 Shift / Alt / Win 都不算，免得误触。切换不产生上屏文本，返回一个「状态变了、无提交」的结果，状态条标点格跟着刷新。

自检：server 68 个测试全过（新增 Ctrl+. 切换、Shift+Ctrl 不触发两个断言），clippy 无代码告警；构建脚本那条 uiAccess 提示是 QINGJIAN_UIACCESS=0 的正常输出，不是代码问题。

### Ctrl+Shift+F 切换简繁

微软拼音拿 Ctrl+Shift+F 在简体和繁体之间切。灰迹的繁体能力本来就完整——OpenCC 转 S2tw，候选转繁体，学习和词库仍按简体记录——设置页也有勾选，缺的还是快捷键。

繁体开关只在启动和热重载时从完整配置设给 Engine，Router 那份扁平配置里没存它。切换方法就直接动 Engine：先给 Engine 加了个读当前繁体状态的 getter，跟 setter 对称；切换时翻转、立即 `set_traditional_mode`，再写回配置文件。当前会话马上变繁体，不用等热重载，下次重载从文件读到的也是新值。

快捷键接在同一个「切换类快捷键」入口，匹配 F 键加 Ctrl+Shift、不带 Alt / Win；只按 Ctrl+F 不触发。

自检：core 302 个、server 69 个测试全过，新增繁体切换用例（打 guo 出「國」、Ctrl+F 不触发），clippy 干净。

### Shift+空格 切换全角 / 半角字符

这是这批里改动最多的一个。青简原来只有「全角标点」开关，没有独立的全角字符模式，打不出全角字母 Ａ、全角数字 １、全角空格 　。所以这个快捷键不只是接开关，得先把能力补出来。

分三块做。一是 Engine 加一个全角字符状态，配一个纯转换函数：空格转 U+3000，其余 ASCII 可打印字符（! 到 ~）统一平移到 U+FF01 起，中文和其他字符不转。二是在按键分流最前面拦截：组句外、全角模式开着时，字母 / 数字 / 空格不再进拼音组词或英文组词，转成全角、吃掉按键、直接提交。标点不在这里处理，仍走原来的全角标点路径，免得两套转换打架。三是 Shift+空格 翻转这个状态，立即同步 Engine、写回配置。

范围刻意收窄：只管组句外（没在打中文词时）的直出字符。全角模式本来就是临时排版需求，进这个模式时通常不在组词。英文候选词整词转全角那种少见又麻烦的情况没做。

自检：core 302、platform 48、server 70 个测试全过，新增全角切换用例（映射、打 a 出 ａ、空格出 U+3000），clippy 干净。

### V 模式补日期、时间

青简原来在 v 模式里只认数字（中文数字、金额）和四则运算，日期时间得靠 rq / sj / xq 三个拼音缩写，而且只能取今天、现在，查不了任意一天。微软拼音的 v 模式是直接打日期串、时间串就出候选，这次把它补齐。

支持几种常见写法。日期：`v2026-10-1`、`v2026/10/1`、`v2026.10.1`，横杠、斜杠、点号三种分隔符都行，但要求年、月、日三段齐全、年是四位。时间：`v12:30`、`v12:30:45`。日期拿 jiff 的 Date::new 校验，13 月、40 号这种过不了，不会硬给。

输出沿用 rq / sj 那几种格式：日期给年月日、横杠、斜杠三种，再额外附一个星期几，查日期的人多半也想知道星期；时间给时:分，有秒再给带秒的，最后补「几点几分」。

几个边界刻意处理了。不做「月日两段、年自动补当前年」：那种写法和算式撞车，v2-1 到底是 2 月 1 日还是 2 减 1？微软把它当减法，灰迹也留给算式，查日期就把年份打全。点号两段（v3.14）同样不抢，留给小数读法。非法日期串（v2026-13-1）正好是个合法连减，回落给求值器出 2012。

自检：core 303 个测试全过，新增日期时间用例（三种分隔符、两段留给减法、小数不冲突、非法回落、时间），clippy 干净。

### 一次排查乌龙：不是安装包卡死，是 UAC 在等人

想在自动化里静默装新包，连续几次都表现为 setup 进程零 CPU、不推进，加 /LOG 连日志都没写，像是卡在安装进程启动的最早期。一度怀疑是提权安装进程加载灰迹 TSF、跨完整性连管道导致的死锁，差点要去改 TSF。

继续查才发现是另一回事。跑自动化的 shell 是未提权（Medium）进程，而安装包要求管理员（PrivilegesRequired=admin）。从未提权进程启动它，每跑一次就在安全桌面弹一个 UAC 确认框（consent.exe）等用户点「是」；自动化看不到安全桌面，也没人点，进程就零 CPU 一直等。任务管理器里 consent.exe 堆了六个，正好对应我跑了六次。

这不是安装包的 bug。输入法安装本来就要管理员授权，双击安装包、在 UAC 点「是」就能正常走完。青简代码里也早有相应保护：拉起 server 的 launch.rs 会先判断宿主完整性，提权、安全桌面、AppContainer 这些进程里压根不拉 server。这次是我启动方式不对——没提权、又没法替用户点 UAC——不是灰迹的问题。

教训记下：要在自动化里装这种 admin 包，得先从提权的 shell 启动，或者明确请用户在 UAC 弹窗点确认，别在未提权的后台反复跑，只会堆一串 consent。

## 阶段 3-q：候选窗自愈

重启后 TSF 确实复位了，但第一次在记事本里打字，老问题还在：拼音进了文档，候选窗没弹。杀掉 server、让 TSF 重新拉起一个，候选窗立刻恢复。这说明它不是上次那种被折腾出来的状态污染，而是一个一直存在的健壮性缺陷，发布前得修。

### 根因

翻当天的 server 日志，登录后 TSF 在几个程序的连接里连续拉起了三个 server 进程。只有第一个抢到命名管道、活了下来，另外两个就绪后发现管道被占、自行退出。活下来的进程建窗成功（日志里没有「建候选窗口失败」），但在多实例同时启动的时序竞争之后，窗口的呈现状态损坏，之后每次输入都不再恢复。手动杀进程后重新拉起的实例没有经历这场竞争，窗口正常。

这是个偶发的时序问题，靠等它复现不现实。修法是让候选窗自己能恢复，而不是依赖手动杀进程。

### 改动

`apps/windows/server/src/ui/candidates/mod.rs`：

- 窗口句柄从固定字段改为 `Cell<HWND>`，把建窗逻辑抽成 `create_hwnd`，使窗口可以在运行中重建。
- 新增 `ensure_window`：每次显示前用 `IsWindow` 检查，句柄失效就重建。

## 阶段 3-t：请求超时与 Server 自动重启（候选窗自愈第 1 步）

### 改动

用户同意先做第 1 步。问题的技术根子是：TSF 把按键转发给 Server 后，在应用的 UI 线程上同步等应答，而管道读写没有超时。Server 一旦卡住，这个等待会无限挂下去，候选窗不弹、UI 线程也被拖住。

- `ClientError` 增加 `Timeout`。
- `EngineClient::call` 改为带超时：把一次「写请求 + 读应答」放进独立线程，主线程用 `recv_timeout` 等待，上限 1 秒（本地候选几十毫秒，端侧整句翻译 P90 约 100ms，1 秒留了余量）。为此连接字段改成 `Option<S>`，超时就把连接随线程作废，泛型加 `Send + 'static`。
- `launch.rs` 增加 `restart_server`：先 taskkill 结束所有 server 进程（同用户无需提权），清掉本进程的拉起冷却，再拉起新的。
- `key_sink` 遇到 `Timeout` 即调用 `restart_server`，本键按「连不上 Server」兜底（拼音字母吃掉防漏进文档，标点 / 数字放行）；新增 `Next::Restarted` 表达这条路径。

杀掉卡死的 Server 还有一个连带效果：其他程序里阻塞在等应答的读操作随管道关闭立即返回，下一键重连，不会一直挂着。

### 自检

## 阶段 3-w：句内标点与大写不再打断，中文模式全力匹配中文

### 需求

用户组句时随手打个逗号，翻译就停了，后面的字母也合不成中文。讨论后定了一个更彻底的方向：中文模式默认全力匹配中文，不再替用户猜「这段大概是英文」；要打英文，明确切到英文模式。大写片段（`PG`、`ID`）原样保留，作为分段边界，前后的拼音分别转中文。

### 根因

`Engine::is_raw` 的规则是「缓冲区出现任何一个非小写字母、非撇号字符就算 raw」。逗号、大写都触发它，于是查询走到 `query_raw`，只给一个原样上屏的英文候选，没有中文、没有译词。这是青简为支持 `no-way`、`hello,` 这类带标点英文串刻意做的，代价是中文整句里不能夹标点。

### 做了什么

- 新建 `engine/query/mixed.rs`，把整串解析成三种片段：拼音段、标点、原样大写段（`MixPart`）。拼音段各自转中文，标点转全角，连续大写原样保留，最后拼成整句。`woaiPGdedongxi` 拼出「我爱PG的东西」，`woai,dongxi` 拼出「我爱，东西」。
- `query_inner` 在 `is_raw` 分岔之前先判混合串，命中走新的分段转换。
- server 收键 `apply_chinese`：大写字母也进缓冲区（原来大写直接直通），删掉那条 passthrough 分支。
- 去掉中文模式的隐式英文：`phonetic.rs` 里三处 `insert_english` 调用全部移除，`extras.rs` 的 `insert_english` 方法、`engine/mod.rs` 的 `ENGLISH_COMPLETIONS` 常量一并删除。
- 翻译适配：`request_prediction` 放行混合串（raw 但属于混合范围的不拦），混合串的 `guess` 直接用拼好的整句，端侧和云端翻译都能拿到带标点、带 `PG` 的原文。

标点只收半角 `, . ! ?` 四种。一开始把 `;` `:` 也算进去，结果辅码和双拼的分号测试挂了——分号在这两个方案里是有含义的，不能当句读。

### 自检

- `qingjian-core` 308 个测试全过，其中混合解析 / 拼接 / 翻译 guess 新增 8 个。
- 随 `insert_english` 删除，三个验证「中英文候选竞争、缩写让行」的旧测试一并删掉，两个验证英文词和补全的改到英文模式。

## 阶段 3-x：候选窗 UI 线程看门狗

### 起因：上一步自愈漏掉了「UI 线程自己卡死」

候选窗自愈第 1 步处理的是 TSF 读管道超时：一次写加读超过 1 秒就作废、杀旧拉新。但有一种卡死它管不到——server 的 Router 还活着、管道在 1 秒内正常应答，只是画候选窗的那个线程卡住了。这时 TSF 每次读都按时拿到结果，不会判超时；候选窗却不再更新、甚至不显示，字照样能打。

这正是「能打字、候选窗不出来」的另一条成因，得让 server 自己在内部发现。

### 做法：请求应答式心跳

Router 本来每秒有一次 tick（节拍不依赖按键，管道空闲也会走）。在这个节拍上挂心跳：

- 每 2 秒经候选窗端口向 UI 线程发一次 Heartbeat。
- UI 线程在自己的消息循环里收到就应答，把共享时间戳更新成当前时间。
- 连续 6 秒没有应答，判定 UI 线程已死，结束整个 server 进程（退出码 77）。TSF 下一次按键发现管道断开，按已有逻辑重拉一个干净进程。

为什么是结束整个进程，而不是只重建窗口。窗口有严格的线程亲和，哪个线程创建的窗口只能由哪个线程销毁；卡死的线程无法响应，别的线程去 DestroyWindow 会失败，残留窗口清不掉。整体重启才有一个干净的起点。

节拍取值偏向保守。一帧渲染在百毫秒以内，2 秒探测一次、6 秒才判死，留了很宽的余量，宁可不动也不误杀。系统时间异常（时间戳还是 0、或者时间被往回拨）时不判死。

### 落地

- 新建 `ui/watchdog.rs`：Heartbeat 持有一个原子时间戳，负责应答、计算距上次应答的时长、判死；带 3 个单测（新心跳不报、超时能报、零时间戳永不报）。
- `ui/command.rs` 加 Heartbeat 命令；`ui/mod.rs` 让 UiHandle 持有心跳和上次探测时间，到点发探测、判死则记日志并退出，UI 线程收到 Heartbeat 就应答。
- CandidateSink 加一个默认空的 watchdog 端口（NoopSink 不用改），Router 在 `rescore` 的 tick 末尾调它。

这是双会话调试拓扑特有的。但它也印证了青简「单实例 + 全局管道 + 会话绑定窗口」在多会话（远程桌面多会话、一台机器多个交互会话同时用）下的固有边界：一个全局 server 没法同时给多个会话画候选窗。真要支持，方向是每个会话起一个 server、管道名带上会话后缀；这属于架构改动，单用户桌面用不上，先记为已知限制。

上一批浸泡只验证了候选能正常出来。这一轮专门压排序：同一个意图分别用全拼、声母缩写、错序手误打，看候选先后合不合理。先在真机灰迹打 sy / sj / xx / cy 四个双字母缩写，再切到微软拼音打同样四个做对照，另测全拼 shouji / xuexi 和错序 nihau / shouij。

### 对照结果

全拼和错序都没问题：shouji 首选手机、xuexi 首选学习；nihau（nihao 打错尾字母）、shouij（i/j 错序）仍把你好、手机排第一。

缩写组里有真问题，也有我先前判断错的地方：

- sj 在灰迹里首选是「SJ 圣何塞」，手机、世界掉出首屏；微软是手机第一、时间第六。
- xx 灰迹首选谢谢，信息直接缺席；微软是信息第一、谢谢第二。
- sy 灰迹首选使用——这其实和微软一致，不算错；但微软第二是所以，灰迹第二是饰演，所以被压到第四。
- cy 灰迹首选次于，微软首选处于；两边都不出「词语」，我先前以为 cy 该给词语，是想当然。

### 根因

那个抢首选的「SJ 圣何塞」是 Latin 专名功能误触发。latin_match 只看「全小写 + 切不成完整拼音 + 英文词表命中」，而 sj 正好是英文词表里 San Jose 的缩写码、又切不成完整拼音，就被当成拉丁词插到第一位。它没区分「带元音的拉丁词」和「纯辅音的中文声母简拼」。

更深一层是排序模型的事，这轮只定位、没改。纯声母缩写现在直接套 lm 的全局一元 P(词)，没有按「缩写条件」重排；而 lm 一元对部分常用词是失真的：信息 -10.4（比谢谢低约 100 倍），手机 -8.0 反被世纪 -7.7 压过。词库自带的原始词频其实更接近实际（手机 99832 远高于世纪 36261），但词级排序用的是 lm、不是这份词频。微软能把手机排第一，靠的是从海量缩写按键里学到的 P(词 | 声母) ，这是数据和模型的活，归到补词库那个任务里一起评估。

### 本次改动与自检

latin_match 加守卫：全小写但不含任何元音字母（a/e/i/o/u）的串一律当中文声母简拼，不给拉丁候选；大写缩写专名走大写分支，不受影响。新增单测 pure_consonant_abbreviation_is_not_treated_as_latin，linux 这种带元音的拉丁词仍正常排第一。

- core 315 个测试全过（新增 1），fmt、clippy 干净。
- CLI 用真机词库复现：sj 候选里「SJ 圣何塞」已消失，首位为世纪；手机排序偏深的问题留给词库 / 缩写模型任务。

## 阶段 3-af：用 wordfreq 重建中文一元，纯声母缩写改走一元先验

### 先把根因钉死：语料语域偏差

上一轮只定位到「lm 一元失真」，这轮把 lm 内部计数扒出来看，问题比预想的更具体。lm 的一元计数和词库词频同源，而句首排序走的是 `<s>` 二元（`log_prob(None, 词)` 实际算的是「词在句首出现」的条件概率，不是纯一元）。把 `<s>` 到各词的计数拉出来：

- sj 对应词里，世纪 25956 最高，时间 18553、世界 17346、手机 15968，世纪略胜。
- xx 对应词里，谢谢 195542 一骑绝尘，信息只有 1024。

这些数字带着明显的语料痕迹。lm 主要训自中文维基，「世纪 / 世界」常作百科文章的开头，「谢谢」几乎不拿来讲句子，「手机 / 信息」也不是百科的高频句首。但打声母缩写发生在日常和工作聊天里，词的优先级正好反过来。微软拼音的模型从真实输入日志学，语域对得上，所以 sj 给手机、xx 给信息。这不是某条规则写错，是训练语料的语域和使用场景错位。

### 修法分两块

一是换一元先验。wordfreq 聚合了字幕、网页、社交等多个语域，中文 Zipf 实测：世界 5.96、时间 5.93、学校 5.62、信息 5.48、手机 5.42、世纪 5.41、谢谢 5.16。信息高于谢谢，手机和世纪基本持平且都在常用区间，方向是对的。写了 `tools/corpus/chinese_frequency.py`：从 lm 反导出的一元 TSV 取词，逐个查 wordfreq，一元计数按 `10^zipf · 10` 生成（最高频词约 6 亿，不顶 u32）。wordfreq 没收录的词（5818 个）不凭空埋掉，用已知词拟合出的「语料计数 → 新计数」比例回退，保住罕见词的相对次序。

二是二元按新边际重标定，不直接混。wordfreq 计数是几千到几亿的新尺度，语料二元计数是另一套尺度，直接相除会让条件概率失真。脚本对每条二元做 `c'(a,b) = c(a,b) · u'(a)/c_orig(a)`，条件概率 `c(a,b)/c_orig(a)` 原样保留，只是把边际换成新尺度。`<s>` 特殊处理：它只作前词、不作目标，计数和二元都留语料原值，句首条件概率不受影响。

三是排序算法分叉。光换数据不够——句首仍走 `<s>` 二元，世纪照样第一。给 `LanguageModel` 加了 `unigram_log_prob`（默认返回 None，不破坏现有 mock），在拼音词级排序里判定「整串都是单声母、没有未切分尾巴」（sj、xx 这种），改走纯一元、跳过 `<s>` 句首二元和个人 ngram 插值。全拼、部分拼写仍走原来的上下文二元。个人在某个缩写下选过的词，本来就通过 choice_weight 和候选 weight 提权，缩写的个性化学习不受影响。

### 自检

- CLI 真机词库：sy 首选使用（和微软一致）、xx 信息回到第 4（谢谢掉出首屏）、cy 参与第一、sj 世纪不再霸首、手机第 11（词级第 7，V 模式时间候选占了中间几格）。
- 全拼与混合无回归：shouji 手机、xuexi 学习、nihao 你好、kaif 开发、woaiPGdedongxi 我爱PG的东西、linux / google 拉丁专名仍排第一。
- core 317 个测试全过（新增纯缩写走一元、部分拼写不走一元分叉两个用例），fmt、clippy 干净。
- 说明边界：wordfreq 是全球聚合词频，给不出「手机在 sj 下条件概率最高」这种缩写专属结论，所以手机不会在全新用户那里稳坐第一；用户选过一次后，choice_weight 会把它学到首位，这和微软靠海量缩写数据、灰迹靠本地个人学习是同一个道理。
- 数据产物 lm.qj 是构建产物、不入库；真机 server / DLL 这轮没重编部署，等这批功能一起验证后再统一打包。

## 阶段 3-ag：路由循环看门狗——主循环卡死也能自己了断

### 这次的故障和上一批不是一回事

用户反馈输入法整个没法用。排查后发现，卡住的 server（32712）装配是完整的：私有提交内存 136.6MB，词库、翻译模型、候选窗渲染器都加载成功，日志里也有「就绪」「命名管道监听中 qingjian-1」。它不是没起来，是起来之后不再干活——管道的首个实例一直占着，客户端 CreateFile 能成功，但发出去的 OpenSession、按键消息一律没有应答。

时间线能对上：物理会话里 Doubao 最后一次成功收键是 18:06，最后一次成功连接是 17:49；这个卡死的 holder 在 18:17 才启动，从它启动之后，没有任何客户端再成功连上并拿到候选。更麻烦的是它一直占着首个管道实例，TSF 每次想重拉 server，新进程都因「命名管道被占」立刻退出，两分钟里撞了 51 次，形成持续的启动风暴，故障从一次偶发卡死变成永久不可用。

### 为什么原来看门狗没兜住

UI 线程看门狗（阶段 3-x）盯的是候选窗渲染线程，但它的心跳是由主路由循环在 `router.tick()` 里驱动的——主循环负责收消息、调 `router.handle`、再顺手发心跳。主循环自己一旦在 `tick` 或 `handle` 里死锁，心跳既发不出去也没人检查，看门狗跟着一起停。它能发现「渲染线程死了、路由还活着」，发现不了「路由线程死了、进程还活着、管道还接受连接」。这正是这次的情形。

### 修法：一条不依赖主循环的看门狗

新建 `ipc/router_watchdog.rs`，跑在独立线程上，自己定时、不靠主循环调度。它每 2 秒做一次普通客户端会做的事：开一条新管道连接、发一条 SyncMode、等应答。这条路径完整经过 accept_loop → serve_connection → 主循环 `router.handle`，任何一环死掉，应答都回不来。连续 4 次拿不到应答（约 8～14 秒）就直接结束整个进程（退出码 77），TSF 检测到管道断开，下一键重拉一个干净的新 server。

判死的窗口特意放宽：本地候选正常几十毫秒，连续 8 秒无应答只可能是真死锁，机器短暂繁忙不会误杀。探测用一个固定的高会话号，不与真实 DLL 冲突。

### 顺带踩出一个构建环境的坑

中途新 exe 两个会话都拉不起来，TSF 日志反复报「启动 qingjian-server 失败，返回值 5」，直接启动也被拒。根因是我构建时环境变量名写错了：build.rs 认的是 `QINGJIAN_UIACCESS`，我设成了少一个下划线的 `QINGJIANUIACCESS`，没生效，于是 exe 按默认带上了 uiAccess=true。未签名又不在 Program Files 的 exe 带 uiAccess 会被系统直接拒绝启动。改成正确变量名、确认构建日志出现「QINGJIAN_UIACCESS=0」警告后，exe 恢复可启动。

### 真机验证

- 健康不误杀：会话1 的 server 连续运行数分钟，看门狗每 2 秒探测一次，全程没有自我了断。
- 卡死能自杀：写了个 ctypes 脚本，挂起目标 server 的全部线程、只放行看门狗线程（看门狗线程启动时用 SetThreadDescription 命名为 huiji-router-watchdog 以便识别），进程在第 8 秒退出，和设计一致。
- 自愈闭环：进程退出后会话6 在几秒内被 TSF 自动重拉，管道恢复；握手探针 OpenSession 正常，逐键发 nihao，候选依次为「你 / 你好 / 你好」，首选与译词都对。
- 全 workspace 测试 635 个用例通过、0 失败（core 317），fmt、clippy 干净。看门狗本身的判定已用真机端到端覆盖，没有再补纯单测。
- 打包照旧等这批功能全部验证后统一打一次，这轮只提交代码。

## 阶段 3-ah：真机 TSF DLL 是旧构建，重编部署后才真正连上

### 看门狗上线后用户仍打不了字

路由看门狗提交后，用户反馈还是打不了字。排查发现物理会话的 server 进程、qingjian-1 管道都在，握手探针逐键 nihao 候选完全正常——server 没问题。问题出在加载进每个应用的 TSF DLL：TSF 日志里反复出现「没连上 Server，吃掉按键」「连 Server 失败：系统找不到指定的文件（os error 2）」。

### 根因：部署的 DLL 早于会话隔离改动

真机注册的 DLL（D:\Qingjian\qingjian_tsf-0.1.5-dev-c50d5cd+.dll，最后写入 18:35）是会话隔离（#57）之前的构建，它连的是不带会话后缀的旧管道名 `\\.\pipe\qingjian`；而新 server 只按会话创建 `\\.\pipe\qingjian-1`。名字对不上，CreateFile 报 error 2，TSF 又按「没连上」把按键吃掉，并不断尝试重拉——新拉起的 server 同样只认 qingjian-1，于是死循环。源码其实早已改对，只是真机这份 DLL 一直没换成新的。

### 处理与验证

用当前源码重编 release TSF DLL（x64 3,573,248、x86 3,359,744），把真机注册路径上的旧 DLL 重命名备份、新版放到同一路径（注册表不动）。另加了一个真机自检例子 `apps/windows/tsf/examples/connect_check.rs`，它直接调用 DLL 自己的 `connect_default()`（管道名由 DLL 内部按会话 id 拼，不手动传名），在物理会话跑出「OK：DLL 已连上本会话 Server」，证明 DLL 现在算的就是 qingjian-1 且能连通。

需要说明生效方式：DLL 已在某个进程里加载后，替换文件不会让该进程立刻换用，已经激活过灰迹的应用要重开才加载新 DLL；全新打开的应用直接生效，重启电脑则全部刷新。这轮没有源码逻辑改动（DLL 源码此前已正确），只提交自检例子与本日志，安装包仍等统一打包。

## 阶段 3-ai：多音字罕见读音不再抢首（读音条件排序）

### 反馈

连续三个截图，首选都是正常人不会讲的话：打 yue 首选「说」（罕见 yuè，古同悦）、打 hu 列表混进「戏」（罕见 huī，古同麾）、打 di'y'g（di yi ge）首选「的一个」而不是「第一个」。用户把验收标准说得很明确：不要求首选正好是想要的，但首选绝不能莫名其妙。

### 根因

排序用的语言模型概率（一元加句首 / 上下文二元）只按「词文本」聚合、不按读音条件化，多音字常见读音的高频率漏到罕见读音上。「的」读 de 词频 10,189,450、读 di 仅 21,162，「第」读 di 是 93,683——按 di 这个读音，第是 的四倍；可模型按「的」这个字算分，把 de 的千万频率和「是的」这个高频搭配全算进来，反而压过第。词库其实早就按读音存了词频（的 di=21162），只是排序没用它，仅在模型完全不认识该词时才拿它兜底。

主流输入法按噪声信道（贝叶斯）做，有两项：P(H) 语言模型、P(P|H) 读音 / 打字模型。灰迹只有前者，后者基本被架空，这才是问题的根。

### 怎么修的

补上缺失的读音发射项 log P(这个读音 | 词) = ln(该读音词频 / 该词所有读音词频之和)。

- `qingjian-dictionary`：Dictionary 加一个懒建反查（词文本到该词所有读音词频之和），新增 `reading_emission_log()`；
- 词级排序（phonetic.rs）和整句 Viterbi（viterbi.rs）两处打分都加上它：单读音词为 0，多音字罕见读音为负（的读 di 约 -6.2、说读 yue 约 -3.1、戏读 hu 约 -3.0），罕见读音自动沉底；常见读音和正常搭配不受影响；
- SpanWord 加 emission 字段，把发射项带进整句路径累计得分。

### 自检

- 单测：dictionary 加 reading_emission_penalizes_rare_readings，core 加 rare_readings_do_not_rank_first（yue 首选月、hu 戏不抢首、di'y'g 首选第一个）。core 318、dictionary 38 全绿，fmt、clippy 干净。
- 真机：重编 release server 部署到 D:\Qingjian（TSF DLL 不用动，排序在 server 侧）；新增探针 examples/probe_input.rs，对部署好的 server 实测——yue：说掉到第 4、越 / 月在前；hu：戏沉出列表；di'y'g：第一个回到首选、的一个消失。
- 安装包仍按约定最后统一打包，这轮先提交代码。

## 阶段 4-0：排序标准答案集——先有一把能量「首选合理率」的尺子

### 为什么先做这个

前面多音字那轮是在挑好的例子上验证，改完用户日常打字仍出怪。没有一份固定的标注集，每次排序改动都是半盲，也分不清「修一个坏一片」。这一步不碰排序逻辑，只把尺子立起来，后面每处改动都在同一份用例上比，数字不许倒退。

### 做了什么

新增 `huiji/评测/排序/首选-标准答案.tsv`，三列「目标汉字 / 拼音 / 上文」，复用已有的 `--eval-text` 评测器（冷启动、不学习、不写用户数据），算首选、前三、前五命中率和字准确率。用例分四组：

- A 多音字单字（yue/hu/di/hang/xing/le… 共 22 个），常见读音的字必须首选；
- B 声母缩写高共识首选（sy 使用、cy 参与）；
- C 真实整句（我想去银行、什么狗屁玩意、第一个… 共 40 句）；
- D 组合自然度（jiushish 应出就是说）。

### 基线数字（改动前）

68 条：首选 97.1%、前三/前五 97.1%、字准确率 97.5%，查询平均 6.2ms、最慢 93.2ms。

两个未命中，留作后面靶子：`xing` 的「性」排第 6（型先）；`shenmegouspiwanyi` 没还原出「什么狗屁玩意」（出什么狗是万一）。

### 一个关键发现

同一条拼音，空白学习器和带个人数据结果相反：`di` 空白时首选第、带个人 user.tsv 时首选的；`hu` 空白时首选胡、真机首选和。说明静态模型这轮读音发射已经修对，**真机里剩下的怪物主要来自个人学习层**——它按字不按读音、且被文件对话框/桌面文字污染，权重又最高，把静态层的修正盖了过去。下一步重点因此放在读音硬闸门接到个人层、以及个人学习去污。

## 阶段 4-1：读音硬闸门——罕见读音一律压后，任何通道不能跨越

### 要解决什么

上一轮的读音发射是「软扣分」：它加在总分上，可个人一元权重、个人 ngram 也是分，个人数据一大，软扣分就被盖过去，真机上 hu 仍出和、di 仍出的。要的是一道硬保证：**只要这个字在当前读音下属于罕见读音，它就不能排到只读这个读音的字前面，个人选过多少次都没用。**

### 怎么做的

- 字典加 `RARE_READING_SHARE = 0.08` 与 `reading_is_rare(词, 当前读音词频)`：该读音占这个字全部读音词频低于 8% 判罕见。
- 词级排序键里，在结构匹配（精确、覆盖、简拼、末音节）之后、**个人 choice 与上下文得分之前**，插入读音层。于是排序先分常见/罕见两层，层内才比个人选择和语言模型分。
- 整句 Viterbi 同样处理：格子候选带 rare 标记，罕见读音词在路径上再叠加固定重罚 -8，常见读音词在这个格子上稳赢。

阈值为什么安全：正经的小读音（重 chong 约 15%、乐 yue 约 16%、降 xiang 约 24%、弹 tan 约 14%）都在线内；漏过来的罕见读音（的 di 约 0.2%、和 hu / 说 yue / 戏 hu 约 4.5%~4.8%）在线外。像 银行、归还、首都 这类小读音大多以整词出现，整词只有一个读音、不受闸门影响。

### 验证

- 无个人数据同口径评测：69 条，首选 97.1%、前五 97.1%、字准确率 97.5%，与上一版**完全一致，零回归**。
- 真机（带着那份被污染的个人数据）：hu 首选胡（和 直接掉出前九）、di 首选第、yue 首选越/月，罕见读音怪物全部消失。
- 新增单测：即使「和」带 50 次个人高权重，打 hu 仍首选胡。
- 一处刻意的顺序变化：单字 hang 的「行」属小读音、降到罕见层，首选变为杭/航（行读 hang 多在「银行」这类整词里，整词不受影响）；标准答案靶子同步改为杭。liao 的靶子原本误标「了」，改为更合理的「聊」。

### 还没解决、留给后面

真机带个人数据时首选率（92.8%）略低于干净数据（97.1%），差别不是罕见读音怪物，而是两类：相邻重复词「就是是」压过「就是说」（归 4-2 组合自然度）；个人数据把 yue/tan/xiang 的常见字做了细微换位（归 4-3 个人学习去污）。
