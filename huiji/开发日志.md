# 灰迹输入法 · 开发日志

> 这是精简后的开发记录，按里程碑记“做了什么、结果、教训”。具体命令和逐行 diff 在 git 历史里，这里不重复。
> 项目从 2026-10-03 起步，基于开源青简输入法（Rust、GPL-3.0-or-later）做增量。

## 一、起步：环境、fork 与地基探针（10-03）

**做了什么**：装 VS2022 生成工具和 Rust；用 gh CLI 登录、把青简 fork 到 noii-y、clone 到 `app/`；配好三道 git 钩子（提交前 fmt + clippy，推送前全量测试）。随后做了一个小到不可能失败的改动——改候选词默认个数，出包、装机、确认在系统里生效。

**结果**：证明“改代码 → 编译 → 安装 → 生效”整条链路走得通，后面所有功能都能照这个循环加。

**教训**：最难的是 Windows 系统集成层，青简已经趟平，所以做增量、不从零重写。

## 二、原型验证

### 2A 整句翻译

**做了什么**：摸清青简已写好云端整句网络层（后台线程发 OpenAI 兼容请求、不阻塞输入）。端侧选定 ctranslate2 + Marian 中英模型（model.bin 75.9MB），加重复惩罚消除译文循环。推理后端试了三种：Ruy 源码编（956ms，不达标）、MKL（Windows 跑不起来，断头路）、最终用 system 后端——直接复用 Python wheel 里预编译的 ctranslate2.dll（内含 oneDNN），建了个本地 ASCII SDK。

**结果**：100 句延迟中位 50ms、P90 101ms、全部 ≤800ms，空译文为 0。

**教训**：先找预编译产物，别自己源码编；SentencePiece 在中文 / OneDrive 路径下打不开，模型和安装目录必须用 ASCII 路径。

### 2B 手误纠错

**做了什么**：建评测基建（CLI 读三列 TSV，每条独立清空、断链、不学习）。试过“干净串一处编辑召回”，实测零提升，证为死路、还原。真正有效的是默认开启“中文优先”。

**结果**：声母缩写首选命中率 66.2 → 77.5，防误纠 98.2。

**教训**：死路要靠实测证伪、别凭感觉投入，结论留档免得以后再试；评测必须冷启动、不学习，否则数据是脏的。合成集救不回的大头，是“输入正好对应另一个合理词”的固有歧义，再往上只能靠语境和个性化。

## 三、Windows MVP 与品牌化

### 品牌替换与独立仓库

**做了什么**：用户可见处全部把青简换成灰迹；内部 CLSID、管道名、crate 名、AppData\Qingjian 保留不动。Logo 定为书法质感的“灰”字、纯黑、透明底、无边框（小尺寸用几何版、大尺寸保留书法）。安装包用 Inno Setup，用户可见处全改灰迹，安装目录内部保留 ASCII 路径。随后建独立公开仓库 noii-y/huiji，把完整提交历史一并推过去。

**教训**：品牌分两层——用户可见的全换成自有，内部技术标识保留，否则会破坏功能。独立仓库保留完整历史，既是 GPL 合规，也保留溯源和致敬。

### 候选窗原创皮肤

**关键认知**：候选窗有两条绘制路径，默认走独立的 qingjian-render（软件位图），只有设 `renderer="system"` 才走 Windows GDI。

**做了什么**：两条路径都换成“石墨深邃”——石墨深灰底色配暖琥珀 accent、圆角、首选词加粗并在左侧加琥珀竖条。

**教训**：系统保留的主题色和质感不算原创，品牌视觉得自己定义色值和材质。

### 游戏兼容

**根因**：候选窗不显示，是多实例下管道反复重连、窗口状态损坏；三角洲全屏卡死，是独占全屏加反作弊，TSF 在游戏 UI 线程同步连管道。

**做法**：游戏模式——前台全屏时整体让位，不吃键、不连管道、不弹窗，按键全部直通。

**结果**：真机自测，游戏内打中文没问题。

### 流行语术语表

**做了什么**：源端替换先写探针，被证伪、放弃；改成译文后处理，规则刻意收得很窄（摸鱼 → slack off、内卷 → rat race）。

**教训**：先探针验证再落地；规则要收窄，否则到处误伤。

### 按键习惯对齐微软拼音

**做了什么**：翻页默认 `-`/`=`、小键盘 +/-；Ctrl+. 切中英标点；Ctrl+Shift+F 切简繁；Shift+空格切全/半角；V 模式补日期时间（只认严格格式）。

**教训**：按键是肌肉记忆，直接对齐用户熟悉的系统行为，不自创。

### 设置入口与退出灰迹

**做了什么**：设置入口放进开始菜单和 TSF 右键，云服务页的 API 密钥用密码框、不回显。退出灰迹时先弹确认框，本地断开、重置，再用 ITfInputProcessorProfileMgr 的 ActivateProfile 切到 Windows 默认输入法，目标 profile 动态枚举、读注册表判断是否启用。

**教训**：旧的 ActivateLanguageProfile 在目标未启用时直接 E_FAIL，要改用 ProfileMgr 并带 FORSESSION|ENABLEPROFILE。

### 候选窗自愈与看门狗

**做了什么**：候选窗句柄失效就自动重建；TSF 调用 1 秒超时、失败自动重启 server。加了两条看门狗：UI 看门狗靠心跳，6 秒无应答就结束进程；路由看门狗在独立线程里每 2 秒以新连接探针，连续 4 次无应答也结束进程（它不依赖主循环，专治“进程活着但主循环不路由”）。另外把管道名和启动锁按终端会话隔离，各会话各起各的 server，server 缺失时有界等待重连（最多 2 秒）。

**教训**：系统级服务要假设自己会卡死，靠外部探针自我了断、让 TSF 重拉干净实例；多会话是真实存在的边界，不能假设只有一个桌面。

### 键盘布局清理：五笔“删不掉”的真相

**根因（重要）**：我一度把系统拼音和五笔的 CLSID 记反了，每次“删五笔”实际删的是拼音。直到 dump 注册表里两个 CLSID 的 Description 和显示资源，才确认 {81D4E9C9} 是拼音、{6A498709} 是五笔。另一处根因是 pre-push 测试加载了德语、国际英语布局却只 Load 不 Unload，布局残留。

**做法**：用 Get/Set-WinUserLanguageList 移除五笔、加回拼音；测试侧加 RAII 自动卸载新布局，并用静态锁串行化布局加载。

**教训**：任何系统 CLSID 判断都以注册表 Description 和资源为准，绝不靠记忆；测试引入的全局资源必须 RAII 清理。

### 句内标点、大写与中英切换

**根因**：标点进缓冲区后被 is_raw 判成原始串，只给一个英文原样候选，中文和译词都没了。

**做法**：新建混合查询，句读标点（, . ! ?）留在句内、分段多次匹配；大写字母分段处理；空格、回车照微软（空格上首选中文、回车保留拼音原文、Esc 删原文）。Ctrl+空格由系统 TSF 层处理，灰迹不监听。

**教训**：改交互前先搜官方文档确认标准行为，不自创。

### 拉丁专有名词候选

**做了什么**：复用英文词表（94568 条，专有名词带规范写法）。整串切不成拼音且命中词表时，拉丁候选排第一；能切成拼音的，专有名词排在首选中文之后；纯辅音串（中文声母缩写）不触发；全大写缩写按大写输出。

**教训**：兜底分支要在真实缩写和原始串上反复验证，防止误触发——一个“原始串兜底”曾在缩写上误触发、破了多个测试，最终移除。

### 联想排序对齐微软

**两个反例**：打 `buzhis` 首选“不知所措”，是词级非精确查找让末尾 s 命中了 suo；打 `huixianshi` 首选“灰显示”，是个人数据在句首权重过高、把短期品牌噪声抬了上来。

**做法**：整句最小片段从 2 个字母放宽到 1 个；个人 ngram 在句首的置信度封顶 0.15。顺带修了一个长期静默失效的测试（`#[test]` 被挤到文档注释同行，根本没运行）。

**教训**：留意测试是不是真的在跑、总数有没有增加；个人短期噪声要在句首限流。

## 四、排序质量攻坚

### 标准答案集

先建了一把能量“首选合理率”的尺子：69 个标准例，覆盖多音字单字、声母缩写、真实整句、组合自然度，全部冷启动评测、不学习。

### 读音硬闸门

**铁证**：用空白 CLI、仅配置、加载个人词库、真机管道四组对照，确认是个人 `user.tsv` 把高频字跨读音顶到首选（打 hu 出“和”、打 di 出“的”）。

**关键区分**：多音字怪物（的读 di、和读 hu、说读 yue，占比极低却被当自由单字）和合法次读（还读 huan、都读 du，几乎只随“归还/首都”整词出现）。按读音占比 8% 设硬闸门：罕见读音字无论个人怎么提权都不能越过常见读音字；整句 Viterbi 对罕见词固定重罚。

### 组合自然度

打 `jiushish` 真机首选“就是是”，因为模型没见过“就是→是”、高频“是”被抬上来。加相邻重复扣分（整词重复、单字叠上一词末字才扣），力度 -4，压成“就是说”。叠词本身是整词、不受影响。

### 个人学习去污

把 7 个个人学习文件移到备份目录、以全新学习器启动，真机首选率立刻回到 97.1%，证实存量污染是直接原因。前向加防护：文件管理器等宿主列入 learning_off，不记个人数据、也不发云端。

### 句首先验配比

孤立打 xing，原首选“型”，而微软首选“行”。试过句首纯一元，首选大降 8.7、多个靶子回归，证明句首二元在干活、整体替换不行、还原。定稿窄配比：句首二元权重降到 0.6（0.6 二元 + 0.4 一元），句中不动。

### 端侧神经重排：实测证伪

用 Qwen3-0.6B 试了三条路：让小模型自由生成拼音汉字，很烂；专用 Reranker 给拼音↔汉字打分全是 0（它按语义相关判，拼音是语音对应）；让通用小模型在候选里当裁判，79.7%，改对 0、改错 12。结论：不集成、不打进安装包。

**阶段结果**：干净评测首选 97.1%、前五接近 100%，首选不再是“正常人不会讲的话”。

**教训**：
- 高频单字跨读音翻盘，根子在个人学习层，要靠读音闸门 + 学习去污，而不是调频率。
- 小模型对“常用程度”的先验比校准好的频率表更吵，让小模型覆盖频率表，方向反了。
- 窄改（闸门、配比）安全；整体替换风险大、容易大面积回归。

## 五、清理与云端

### 本地清理（10-06）

删掉探针模型（1051.9MB）、`app\target`（34.7GB）、真机 39 个旧备份和废模型。C 盘剩余 47.3 → 76.2GB，`D:\Qingjian` 从 867MB 降到 399MB。

**教训**：探针得出结论立刻删，新构建验证后旧备份最多留一个，target 定期清——“先留着以防万一”是垃圾的共同来源，git 已经替你做了全部备份。

### DeepSeek 云端共存与严格纠错

**根因**：Engine 只有一个 predictor 槽位，本地翻译每次都把云端覆盖掉，纠错从没跑过。

**做法**：新增 DualPredictor，云端和本地并行；字段拆开——`sentence` 放可 Tab 上屏的中文纠错（独立云朵行），`translation` 放只展示的英文译文（拼音行右侧）。云端语义从“扩写补全”改成“严格还原用户本意”，并加长度护栏，超长的续写直接丢弃。真机还发现并修了一个合并 bug：云端后到的空字段原本会冲掉本地更早返回的译文，改成按字段合并、空词不覆盖。

**两个真机环境事实**：交互桌面是会话 3（不是会话 1），部署、杀进程要覆盖所有会话；`cu.type` 是 Unicode 注入、绕过 TSF，真机打字必须逐键 `cu.press`。

**结果**：打手误串，云端行干净给出“什么狗屁玩意”，Tab 上屏正确；打正常整句，首选中文正确、拼音行右侧稳定显示英文译文。全 workspace 测试、fmt、clippy 全绿。钱是小头，每月约 1～3 元（测算）；API key 只写在本机配置，不进 git、不进安装包。

**教训**：共存要想清楚字段归谁、先后到怎么合；真机“明明改了没效果”，先查部署有没有覆盖正确会话、真机二进制是不是最新，别急着怀疑算法。

### v0.1.6：第一个完整版本发布

功能稳定后统一打包。重写 README，把游戏兼容、离线排序、云端纠错、设置与 API key 用法讲清楚；Windows 三个 crate 版本号升到 0.1.6。release 全量构建 + Inno 出包，真机静默安装验证：64/32 位 TSF 注册都指向 0.1.6，词频、翻译模型、运行时齐全。GitHub Release v0.1.6 标记为 Latest，旧 0.1.5-beta 保留为预发布。安装包 128 MB，模型和运行时全打进，装完离线可用。

**教训**：打包放最后、功能攒齐再做，避免反复迭代出包；发布前真机静默装一遍、核对注册和随包文件，比只看编译成功可靠。

### 品牌渗漏收尾（换机后）

换机装 v0.1.6 发现默认路径仍是 `C:\Program Files\Qingjian`，设置里也残留青简字样。分四批修：

- **文案**：渲染器、关于页、云页统一为灰迹；「本地整句模型」开关按实情改为默认空操作（v0.1.6 并未随包神经模型）。
- **安装路径**：默认目录改 `Huiji`，构建脚本去掉硬编码的旧电脑路径，可用参数覆盖。
- **五笔**：从设置、打包清单、数据、署名全部移除；核心的通用形码能力保留但休眠。
- **设置分层**：通用页只留 8 个日常项，冷门项收进「高级」页。

换机构建缺链接用的 `ctranslate2.lib`（安装目录只带运行时 dll）。用 dumpbin 从已装的 ctranslate2.dll 导出符号表、生成同版本导入库，保证 ABI 一致；生成数据和翻译模型从现有安装目录取回。三包 check、平台 49 项单测全绿。

**教训**：对外可见的名称要在安装路径、设置、关于、打包清单各处对齐；换机构建先核对 SDK 链接库和生成数据，缺 .lib 就从同版本 dll 反推，别下版本不一致的官方 SDK。

### v0.1.7：版本化发布、构建可复现、占用自动清理

- **版本号**：三个 Windows crate 升到 0.1.7。真机从 0.1.6 升级：新版 DLL 并排装、CLSID 指向 0.1.7，旧 0.1.6 DLL 当场删掉，没留残留。
- **占位库自动生成**：ct2rs 在 Windows 上会让链接器无条件找 cublas / cublasLt / cpu_features，即便只走 CPU、没有符号引用它们。build.ps1 缺这几个库时，用 vswhere 定位 MSVC，编一个不引头的空目标各自打成静态库占位，换机也能直接打包，不用再手工建。
- **占用自动清理**：覆盖前杀进程、能改名就改名；删不掉的用 MoveFileEx 登记重启删。旧目录 `D:\Qingjian` 的 DLL 和目录已这样登记，重启自动清掉，不留手动步骤。

**教训**：环境依赖让脚本自动补齐，比写进文档靠人记得可靠；遇到文件占用别只把“请重启”丢给用户——能删即删，删不掉自动登记，重启后系统自己收尾。

### v0.1.8：静默安装后 Server 必起、单实例保险

换机装完 0.1.7，输入法没反应。根因是安装脚本里装完自动起 Server 的代码挂在完成页、且只在非静默时执行。0.1.7 用管理员静默方式装：旧 Server 先被杀，静默模式跳过完成页启动，唯一的登录自启要重新登录才跑，又没注销，于是没有任何 Server 在运行。按键兜底那套有多道闸门（宿主必须 Medium、安装互斥体不能在），这次也没接住。

两处改动：

- **安装器任何模式装完都起 Server**：启动从完成页挪到 `ssPostInstall`，静默、非静默都触发，仍用 ShellExecAsOriginalUser 以原用户、可获 uiAccess 的方式拉；没有可交互用户时安静跳过，交给登录快捷方式。不用高权限兜底，否则普通权限的输入法连不上管道。
- **Server 加单实例互斥体**：main 最早期建 `Local\QingjianServer-<会话>`，第二个实例退出码 0 立即退出。同名管道本来就允许多个实例，以前“只起一个”靠启动时机，安装器和已开应用里的 DLL 同时拉，就会冒出两个 Server、两条状态条；有了互斥体，几条路径一起拉也只活一个。

真机验证：管理员静默装 0.1.8，装完没注销、也没打字，Server 已在跑、管道在；再手动起一个实例，退出码 0、进程数始终为 1；打字候选窗正常、首选正确、只有一个窗口。

**教训**：自启动不能只挂在有界面的完成页，静默路径得同样覆盖；“只起一个进程”不能靠各启动路径自己守时机，得让进程用互斥体兜底。改启动路径前先想清楚 uiAccess 从哪来，计划任务、高权限启动都拿不到，会顺手把候选窗覆盖系统界面的能力改没。

### README 图片国内可见、banner 压缩、数据备份说明

有人反馈仓库首页两张图（主视觉、候选窗截图）在国内直连下裂成破图，三个徽章却正常。抓 GitHub 页面 HTML 逐层定位：README 里图片用的是 `github.com/.../raw/main/...` 同源直链，GitHub 对自家 raw 不做 camo 代理，浏览器会 302 到 `raw.githubusercontent.com`；而国内默认 DNS 把这个域名解析成 0.0.0.0（DNS 黑洞），于是图裂。徽章图来自外站 shields.io，GitHub 走 camo 代理，camo 域名在国内能解析、能连，所以正常。

不是仓库文件、路径或推送的问题，是图片引用方式叠加网络污染。修法是把两张图换成 jsDelivr CDN 外链：它成了外站图后，GitHub 同样用 camo 代理，浏览器只连可访问的 camo，由 GitHub 服务器回源取图。引用用不可变的完整 commit hash 而不是 main，避开 CDN 缓存。

顺带做了三件事：

- **压缩 banner**：原图 2730×1536、3.7MB，压成 1800 宽 WebP(q86)，256KB，深色噪点和文字肉眼无损；make_banner 改成脚本相对路径、直接产出 WebP，不再写死电脑用户名，也不把超大 PNG 存进仓库。
- **数据备份说明**：README「数据与隐私」和设置「高级」页的「数据目录」字段写明：学习数据在 `%APPDATA%\Qingjian`，覆盖安装、升级都不删除，换电脑复制整个文件夹即可带走习惯与设置。
- **验证不止在本机自欺**：抓真实页面 HTML，确认两张图已被包成 camo 地址并逐张 200 取到完整字节，再在浏览器真机看到两张图正常显示，而不是改改本机 hosts 能看到就算修好。

**教训**：面向国内用户的门面，图片别用 GitHub raw 直链，走 jsDelivr 这类 CDN 让它落到 camo 代理上；判据是抓真实页面里图片实际走的域名和返回码，而不是“我本机网络能看到”。

### 前后鼻音容错方向：漏 g 先补韵尾，不当换声母处理

打 `wo'min'tian`（min 漏了 g，本意是"明天"）时，本地首选却是"我今天"，"明天"根本排不上。min 是中文里最常见的前后鼻音漏打，这是本地引擎该自己做对的基础题。

纠错变体给 min 同时生成了两个候选：`ming`（末尾补一个 g，算漏键）和 `jin`（首字母 m→j，算相邻键误碰）。问题出在代价表：漏键 5.5、相邻键替换 5.0，补 g 反而比换声母还贵 0.5，再叠加"今天"是超高频词，"今天"就压过了"明天"。代价方向反了：补韵尾保留声母、只动韵母，是中文里系统性的前后鼻音；换声母则把整个音节换成另一个字，信息损失大得多。

- 新增一个只认"韵母末尾多/少一个 g、声母原样"的判定（min↔ming、gan↔gang、zhen↔zheng），给独立代价 3.5，明显低于相邻键替换；其他补键仍是 5.5，不把 gan→guan 这种补介音也一起放宽。
- 阈值靠扫参实测而不是拍脑袋：漏键代价降到 4.0 才翻转，留余量取 3.5。

验证：core 323 个单测通过（新增判定单测和端到端排序单测）；首选答案集从 69 句加到 77 句，新增 8 条前后鼻音，首选合理率 97.1%→97.4%，精确的 jintian（今天）、renmin（人民）没被带歪；release CLI 用产品词库确认 womintian→我明天、womintianxiangxiuxi→我明天想休息。

云的定位也随之收紧：前后鼻音、邻键误碰这类本地理应自己搞定的，不再拿来当云端纠错的展示点。云只留给本地结构够不到的长句整句语义，README 同步改写，旧的 womintian 云截图撤下、换成真正需要整句语义的例子。真机部署用 `huiji/tools/deploy-local.ps1`，以管理员身份运行即可把新 server 覆盖到安装目录，不必重打安装包。

**教训**：容错代价要按"信息损失"分档，保留声母只动韵尾是系统发音规律、换声母是另一个字，两类不该一个价；调阈值先扫参找翻转点、再留余量，别拍脑袋。本地能自己做对的基础题不要丢给云兜底，云的展示点要能体现它真正不可替代的场景。

### 系统发音纠错：平翘舌漏 h 与常用多字词补全

前后鼻音（漏 g）修好后，又冒出同类问题。打 `chengsi` 想写"城市"，首选却是"撑死"；`laosi` 出"劳斯"不出"老师"。这些不是手滑，是平翘舌：很多方言区的人不发声母里的 h，把 shi 打成 si、chang 打成 can，和漏尾 g 是一类系统发音。老的纠错代价把"换声母"和"漏 h"混在一个价里，本地没法纠。

先把每个纠错边按性质分类：`Original`（原样）、`Phonetic`（漏 g / 漏 h 的系统发音）、`Physical`（相邻键误碰、换位等随机手滑）。平翘舌漏 h 给独立代价 3.5，和漏尾 g 同档；随机手滑维持高代价。只有 `Phonetic` 边的句子不算"敲错"，不再因为一处发音习惯就整体退回原样。

真正难的是城市这类临界情况。城市在词图里本来就排第一，语言模型也判它比"撑死"可能 3.25（log 空间），但固定发音纠错代价恰好是 3.5，"撑死"靠"零纠错"以 0.25 的微弱优势翻盘。这个固定值的含义是：纠错词词频得高 exp(3.5)≈33 倍才翻得动，城市/撑死 40 倍只有 0.2 的余量，被句首 bigram 的噪声抹平了。

试过两条简单路子，都被实测证伪：全局把代价降到 3.2/3.0，答案集对 retroflex 不敏感、覆盖不到；只要"纠错词是常用多字词"就把惩罚降到 2.0，立刻引入两个回归——`wangshan` 翻成"晚上"（晚上要改首尾两处，被一起降了罚）、`siji` 翻成"世纪"（世纪只比原样词司机高 2.5 倍，可司机本身就是常用词）。

最后改成两阶段、四个条件同时满足才降代价：只有漏 g/h 的发音边、没有随机手滑边；恰好改一处（首尾两处都改的"晚上"不补）；纠正出来是多字词且词频过一万（单字不补，ran 就该先给然，"金恩"这种两个单字硬凑的假词也拿不到）；词频还要达到原样能拼出的最高频词的 3 倍（城市/撑死 40 倍、老师/劳斯 114 倍该翻，世纪/司机 2.5 倍守住原样）。另外 `wangshan` 的"网上"在词级前缀补全阶段被压，单独修了 count>=2 的前缀补全，只对漏 g/h 命中的词放开最后一个音节。

验证：新增两个端到端单测，一个锁城市/老师该翻、司机/晚上/网上该守的边界，一个锁单字不补偿；core 单测 325→327 全过。答案集加了 H 组 35 条临界正反例（该翻的常用词、必须守住的原样常用词、单字），91 句扩到 126 句，首选 97.8%→98.4%、字准确率 98.1%→98.5%，两个既存 miss（多音字"行"、复杂错字"什么狗屁玩意"）之外没有倒退。双重错误（经常 jingchang 漏 h 打成 jingcan，声母韵母各错一处）这轮不处理，留给整句和云兜底。

**教训**：不要用一个全局常数去调纠错松紧，调来调去都会在别处翻车；要把"什么情况下该宽容"写成结构化条件，而且每条放宽都得配一个反例防它过度纠错。判定一个改法对不对，光看正例不够，必须同时准备一批"原样就很合理"的反例，再让答案集数字说话。改完排序，单测、答案集、正反例 CLI 三样都要过，真机二进制要重编覆盖。

## 六、方向重构：真实语料打穿自造答案集，云当长句主力（10-14）

平翘舌那轮把发音纠错的常数调到头后，发现自己一直在做一件低收益的事：用自造的 126 条孤立拼音答案集（首选 98.4%）证明改法有效，但真实打字首选还是乱（buzhis 出"不知所措"、wo'min'tian 出"我今天"）。于是停下来，换真实文本重新量。

用六类开源语料（外卖、酒店、电商评论，Tatoeba 日常句，人民日报，红楼梦，共 16.7 万句），先把汉字转成拼音、再喂给引擎，看本地首选：

- 现代口语和书面语首选率只有 50%–61%，字准确率 86%–90%；前三只比首选高 5 个点，错了翻页也找不到。自造答案集的 98.4% 是按引擎能力出题，属于自我循环。
- 抽 102 句用相同提示词走 DeepSeek：整句正确率 51%→75.5%，本地错的句子云救回一半，本地对的云只改错 1 句。云救的是同音实词按语境选词（饭/但、明/今、门童/门通、当即/党籍），正是统计引擎的结构短板。
- 成本：每句约 549 token，固定提示词命中上下文缓存，单句约 0.0008 元（高峰测算），重度用户一个月几块钱。

另一个发现：长度和"本地有没有组出整句"都判断不了本地对错——短句首选也只有 57%，本地 99.8% 的句子都会给个整句。本地对错误没有自知之明，简单触发规则不可靠，好在云足够便宜。

由此定下新方向：**云管长句整句、本地守短句和离线兜底，不做本地神经模型**。阶段 1 做云整句触发、磁盘持久化缓存、真机整句 Tab 接受；阶段 2 摘掉 candle 神经模型；阶段 3 只按真实高频错例补词库。评测脚本、语料处理和结论放在 `huiji/评测/真实语料/`，原始大文件不入库，脚本可复现。

**教训**：评测集决定你能看到什么，按引擎能力造题会自我循环、越调越偏，必须用真实分布的语料，先量再改、不靠手感。统计模型在整句语境上有结构性天花板，这种地方继续手工调常数是和数据对着干；但也别把所有事都丢给云——云晚到、要花钱、有隐私边界，本地守住短句和离线，复杂语义才上云。

## 七、云整句 Tab 选中与外文跟随首位（10-14）

第六节定下「云管长句、本地守短句」后，真机用下来有个断链：云把整句中文纠错出来了，按 Tab 中文直接上屏，可顶部那行外文还是按本地组错的整句翻的。比如本地首选是「我今天」，云纠成「我明天」，上屏的是明天，旁边英文却写着 today。根因是中文纠错走云、外文翻译走本地 Marian，两条链路互不知道对方；Tab 上屏后没人用正确中文重译一次。

交互按用得最顺的方式定，不做自动替换：

- 按一次 Tab，云整句从云行提到候选区首位，但不上屏，仍然停在组词状态；顶部外文立刻翻这句正确的中文。
- 空格或回车才上屏；Esc 取消选中、拼音和云行都留着；继续打字、翻页、按数字选本地词都会退出云首位。
- 云整句在首位时再按 Tab 不翻走；云还没到时 Tab 照常翻页。
- 用加减号或方向键翻到某个单词候选，顶部外文也跟着翻那个词。
- 外文让云在给中文的同一次请求里一起返回，Tab 切换时零等待；云没给或离线时，本地模型照旧兜底。

实现上，云提示词的输出加了一个 translation 字段，并且和 sentence 绑定：整句不成立时译文一并丢弃，避免出现中文上屏了、英文对不上的情况。Router 加了云选中状态和云译文两个字段，Tab、Esc、回车、翻页、数字选词各自决定进不进、退不退出这个状态。云行选中后直接画成一条首位候选：高亮底、序号 1、云朵、加粗整句，右侧标「空格上屏」。

踩了一个状态机的坑：Esc 取消选中最初返回的是「内容已变」，主流程据此重新组句，把刚到的云整句一起清掉了，云行闪一下就没。新增的单测当场抓到。改成 Esc 只取消选中、返回「仅导航」，不重新组句，问题才消失。这也理清了一条边界：凡是不改变拼音的操作（选中、翻页、取消）都不该触发重新组句，重新组句只留给真正增删字母。

验证：render 6、platform 46、predict 25、core 327、windows-server 17，共 421 个库单测全过，其中新增 7 个（云提示词译文绑定 1 个，Tab 选中、空格/回车上屏、Esc 取消、翻页退出、无云翻页 6 个）；release 构建通过。

真机部署踩了一个坑。`apps/windows/server/build.rs` 默认把 server 编成 uiAccess=true，未签名的 exe 系统直接拒绝启动（os error 740，Start-Process 报要提权），TSF 连不上管道、云完全不触发。开发期真机必须先设 `QINGJIAN_UIACCESS=0` 再 build，出来的是 asInvoker 普通 exe 才能起。第一次部署错就错在覆盖进去的是没带这个环境变量编出的版本。正式对外打包也按这个口径，否则用户装完同样起不来。重启后 server 能自己拉起，不需要人工干预。

记事本真机逐条验证通过：

- 云行不抢首位：打 `xianzairenaodedifang`，本地首选仍是「现在人我的地方」，云朵行单独待在候选区上方。
- 一次 Tab：云整句提到首位（高亮、序号 1、云朵、右侧「空格上屏」），不上屏，仍组词；顶部外文同步成 the place where people are making a fuss now。
- 再按 Tab：停在云首位不翻页。
- 空格：云整句上屏。
- Esc：退回未选中云行，本地首选恢复首位，外文清空，拼音和云行都保留。
- 方向键翻单词：打 `ming`，首位「名」顶部外文 name，移到「明」变成 bright。
- 没有云行时 Tab 照常翻页：打 `nihao` 按 Tab，页码 1/9 翻到 2/9。
- 外文零等待：云在给中文的同一次请求里返回译文，Tab 瞬间出译文，缓存命中秒出；云超时或离线时本地候选照常显示。

真机暴露、留到后续阶段的三个问题：云请求 5 秒超时对长句偶发偏紧，阶段 1a 定触发策略时一起调超时和重试；连写 `renao` 被切成 `ren'ao`（人闹）而不是 `re'nao`（热闹），是音节切分问题；`ming` 单字首选是「名」不是「明」，归阶段 3 的词库和排序。

**教训**：一个界面上同时显示的东西（中文和它的外文）必须来自同一份数据，要么一起改、要么明确绑定，不能各走一条链路再指望事后对齐。状态机里「内容变了」和「只是看了一眼」要分开，否则一个导航动作会误触发数据重建。

## 八、云触发门槛与真机验证（10-15）

第七节把云整句接进了候选，但当时只要敲够两个字母就发云，几乎每次按键都在请求。短词本地本来就很准，这些请求既花 token 又没有收益。这一节用阶段 0 的语料数据重新划了触发线。

本地首选率随句子变长往下掉：1-3 字约 60%，4 字 55%，9-12 字 44%，13 字以上只剩 36%。云的救回也集中在长句——阶段 0 抽样里 4 字以上发云，94% 的情况下能纠回本地的错，5 字以上没出现过云把对的改错。反过来看 126 个短词答案集，本地首选率 98.4%，短词没有上云的必要。

按这个分布定了三档门槛：

- 1-2 个音节不发云，本地直接给。
- 3 个音节起发云词（帮补手误的词），但不返回整句。
- 4 个音节起才同时要云词和整句。
- 缩写（只打声母）不要云词；问字模式照常要词；整串是切不成拼音的拉丁词（linux、hello）直接早退，不发。

另外把云请求超时从 5 秒放宽到 8 秒，失败不自动重试，防抖维持 300 毫秒。不重试是为了避免网络抖动时一串请求堆着，超时就退回本地候选，下一键防抖后自然再发。

这轮还修了一个会直接让云静默失效的问题：模型名 `deepseek-v4-flash` 已经下线，官方 `/models` 现在只列 `deepseek-flash`（V4.1-Flash）和 `deepseek-v4-pro`。代码默认值、配置模板、词条生成工具、评测脚本里四处旧名字一并改成 `deepseek-flash`，超时默认值也统一成 8000 毫秒。

真机验证踩了一个很费时间的坑。一开始用桌面自动化逐键打字，候选窗看着正常、中文也能出，但后台日志里一条云触发都没有。排查到最后才发现：自动化在带提权窗口的环境里，模拟击键没有真正进入目标窗口的 TSF 通道，屏幕上那个候选窗是全局悬浮窗跟着鼠标位置画出来的假象。改用物理键盘打字，门槛日志立刻全部出现。之后真机验证云触发只认物理键盘，不再用模拟击键下结论。

物理键盘在记事本里的实测和设计一致：

- `wo`、`wo'shi`、`fa'ge`（1-2 音节）不发云。
- 只打声母的 `wo's`、`wo'sh` 不发云词。
- `fa'gei'ta`、`wo'shi'gao`（3 音节）发云词、不返回整句。
- `fa'gei'ta'm`、`wo'shi'gao'yuan`（4 音节）同时要云词和整句。
- linux 这类拉丁词早退。

云请求确实正常发出并连到了 api.deepseek.com，但当天服务端一直没有恢复：最小请求能收到 HTTP 200 响应头，正文却二三十秒不返回，输入法 8 秒后按超时退回本地。查过余额和 key 都正常（余额 10.21 元、is_available 为真），本机也没有代理和 hosts 干扰，属于服务端临时故障。所以这一节的代码、门槛、请求链路都在真机验证通过，云端整句正面显示和 Tab 交互的最终效果要等服务恢复后再确认一次。

## 九、离线翻译摸底：调参压重复，语义交给云（10-16）

起因是离线模型把"我今天想吃苹果"翻成 I want apples today，漏掉了"吃"。这不是偶发，是端侧小模型的质量问题。

拿 100 句日常话重新摸底，发现之前 3.53 分的评分是在加重复惩罚参数之前跑的，不代表现状。用 translate_probe.py 在同一批句子上对比三组解码参数，按 100 句里有重复退化的句子数算：

- 默认参数（rep1.0/ngram0）：78 句复读，连续重复词 70 处、重复片段 507 处。
- 真机旧参数（rep1.2/ngram3）：21 句复读，连续重复词 16 处、重复片段 58 处。
- 本次新参数（rep1.4/ngram2）：8 句复读，连续重复词 7 处、重复片段 11 处。

新参数把剩下的复读基本压掉，也没看出语法崩。于是把 local_translator.rs 的解码参数定到 rep1.4/ngram2，结果存为新基线 `端侧-int8-rep14-ngram2.tsv`。

但数字、术语、网络流行语的误译调参解决不了：三分糖成 three cents、高铁成 high-calk、房租三千二成 $32,000、破防成 breaking up our homes。这是 81MB 模型的能力天花板，再调常数也上不去。

这部分的分工就此定清楚：

- 联网时翻译走云。实测 DeepSeek 对摸鱼、破防、绝绝子、神仙颜值、内卷以及两句古文都能正确意译，不需要给离线模型补流行语词库，词变体补不过来，探针也证明源端塞英文会被模型拆碎。
- 离线模型只在断网、超时时兜底，调到"能看"即可。
- 更强的离线模型（NLLB 一类）体积和 CPU 开销都大，以后做成设置里按需下载，这次先不做。
- 不删离线模型，也不接第三方免费翻译接口。前者会丢掉断网时的英文，后者要各填各的 key、有的还要绑卡，而且联网时 DeepSeek 已经够用，再接一个是重复。

顺带修了一个一直没被跑出来的坏测试：`组句请求标记为compose` 把测试文本放在了 text 字段，而 Compose 路径实际读的是 guess，和"整句 guess 为空被忽略"的测试互相矛盾。它在 local-nmt-system 特性下才编译，平时没开这个特性所以没暴露，改成把文本放到 guess 后与真实路径一致。

predict 37 项单测全绿，release 编译通过。这次只改参数，不单独部署真机，和后面的云翻译补全一起换一次 exe。

## 十、云结果磁盘缓存：同一句只花一次 token（10-16）

之前云端结果只留在内存缓存里，程序重启就清空。一句话如果经常打，每次开机都要重新请求一次，既慢又费 token，断网时也借不上以前的结果。

加了一个磁盘缓存 `cloud-cache.json`，和配置、学习数据放在同一个用户目录。键只看请求本身，不看临时上下文：组句用 `C`、问答用 `Q`、翻译用 `T` 三类前缀，带文件格式版本号和 2000 条上限，超了按最久没用到的淘汰。读取在内存缓存之后、发网络之前，命中磁盘就回填内存，同一次输入里继续退格重打只走内存。

真机重启后能直接读出之前存的 44 条，打字一阵涨到 60 条，其中翻译结果 4 条。组句的完整结果、补全翻译的结果分别按各自的键缓存，同一句第二次打走内存，换个时间再打走磁盘，云端只在第一次花钱。

## 十一、云翻译补全：长句别再退回漏词的离线译文（10-16）

离线调参后漏词仍然存在，因为有些场景顶部根本没走到云端翻译。具体是这样：本地已经组出完整长句（比如缩写 p g 也能组出"我今天想吃苹果"），但云端纠错对没把握的输入只回词、不回整句。原来的逻辑拿不到云整句，顶部就退回端侧 opus-mt，于是出现 I want apples today 这种漏掉 eat 的译文。

改法放在后台 worker 内部，不碰排序和状态机：组句请求拿到"既没整句也没译文"的回复时，如果本地已经组出 4 个音节以上的中文，就用选中文字翻译那套提示词，拿这句中文再发一次中译英，译文填回组句结果一起返回。补出来的翻译和普通翻译共用内存和磁盘缓存，同一句只花一次 token；断网、超时补不到就保持空，顶部交给端侧。翻译请求本身不再触发补全，递归最多两层。

这样顶部译文的顺序是：云端同次给的整句译文优先，其次是这次补出来的云端译文，最后才是端侧 opus-mt；联网时翻译统一走云，断网时仍有英文兜底。

验证情况：

- predict 单测 42 项全绿，其中 5 项专门覆盖补全触发、短输入不补、空句不补、翻译请求不递归、目标语言缺省补 en。
- cli 端到端和真机后台日志都看到"云未给整句，补一次云端中译英"。"我今天想吃苹果"得到 I want to eat apples today，eat 不再漏；测试期间一次网络请求失败，端侧照常兜底，输入没有卡住。
- 补全翻译按 T 类键落盘，跨重启同样的句子直接命中缓存。

这条只解决译文缺漏，不保证中文本身正确：本地首选中文组错时，云端翻译会忠实地把错句译出来。中文首选准不准是另一块（见后面的阶段三），不在这里硬补。

## 十二、上游青简补丁同步：只补缺的，不照搬（10-16）

fork 基线（0.1.5-beta.1）之后青简主分支推进了约 240 个提交。逐个过了一遍，按"灰迹确实缺、又不违背云为主这个方向"的标准挑，含章本地模型、macOS、其他学习语言这几类直接不拿。

## 十四、翻页边界与摘除含章本地模型（10-16）

翻页边界对齐上游 537 号补丁。中文组句时用 `-` `=` 翻页，翻到首页再往前或末页再往后，原来这一下是被吃掉的，键没了、页也没动。现在翻不动时把原字符落进当前英文直输段，和微软拼音的行为一致，键不白按。`[ ] , .` 这几个翻页键在翻不动时照旧吃掉，不往文档里插标点。server 加了一个单测，用每页 4 个、共 3 页的自定义词把首页、末页两个边界和 `[ ]` 分支都覆盖到。

摘除含章本地神经模型是这一轮的主线。灰迹的方向在前面已经定了：长句纠错和翻译走云端 DeepSeek，离线只留 opus-mt 做词级翻译兜底，本地中文神经模型不做。含章官方自测的首选命中率只有 42.5%，自由生成 51.9%，单次 130 到 200ms，达不到实时；云在同一份句子上是 75.5%，还附带整句翻译。保留含章既没有效果优势，还拖进整套 candle 依赖，是 target 体积膨胀的主要来源。

摘除分两步做，每步都能单独编译回退：

第一步摘 server 的加载链。删掉 rescore 的 loader 和 ModelLoader，find_model 固定返回空，开机不再找模型文件。core 里的 rescoring 框架保留，只是永远不挂 scorer，相关调用全部空转，这样 core 的引擎结构和上游保持一致，以后合并补丁不冲突。opus-mt 的 ctranslate2 链路原样保留，离线翻译不受影响。

第二步把含章从开发工具链也摘掉。cli 删掉 `--neural` 系列、`--eval-p2c`、`--eval-generate`、`--cold-model` 这些神经实验参数，以及 eval/generate.rs、eval/p2c.rs 两个文件和冷启动评测里的 P2C 生成；dict-convert 删掉 model（.qjm）打包子命令。然后把 crates/qingjian-neural 整个 crate 从工作区删除，candle 0.11 的版本声明一并移除，apps/linux、apps/macos 移出 workspace（灰迹只发布 Windows，两个目录留着对照上游，不参与构建）。静态评测要用的 `--eval-text`、`--eval-cold`、翻译探针都保留，词库评测这条链不能断。

验证：`cargo tree -i candle-core` 在整个工作区已经找不到这个包；cli、server、predict、tsf 四套单测分别是 12、20、44、18 项全过；离线跑三句 eval-text 首选 100%，词库和语言模型加载正常。release server 可执行文件从 18.2MB 降到 15.0MB。

顺手清了构建垃圾。target 一度到 21.9GB，主要是 debug 开发构建的调试符号和多轮实验产物。删掉整个 debug 目录（18.3GB）、deps 里残留的 candle 产物（660MB）和两个旧版本安装包（GitHub 已发布），target 回落到 4.9GB，其中 release 是发布构建缓存、i686 是 32 位 TSF，都留着给统一打包用。端侧 opus-mt 模型 79.6MB 在 AppData 里，是离线翻译兜底，没有动。

摘含章还漏了一个用户可见的尾巴，这次补上。设置→云服务页原本第一行是"本地整句模型"开关，写的是 `[model] enabled`。模型 crate 删掉后，这个开关拨了没有任何反应，是纯空转。这轮把配置结构、设置页开关、消息分支、server 启动和热加载里的模型配置链路一起删干净：platform 的 `LocalModelConfig` 结构和配置模板里的 `[model]` 段移除，server 删掉 find_model、configure_local_model、apply_model_config 以及 Router 里的 model_path、applied_model 字段，设置页删开关和对应消息。rescoring 调度框架仍保留，不挂 scorer 时全部空转，其中光标前文还在给云端 before 用。

这里有一个升级兼容点要确认：老用户配置文件里已经写了 `[model] enabled = true`，新版结构没这个字段，反序列化时必须忽略而不是报错。为此加了一个单测，用带 `[model]` 段的旧格式文本解析，确认能正常加载、其它字段不受影响。配置没有开 deny_unknown_fields，多余的分节会被忽略，等设置保存一次自然就消失了。platform 48 项、server 20 项单测全过，platform、server、settings 三个 crate 各自 cargo check 都通过。

摘含章之后，排序的问题收敛到一个明确的根因上。真机打 henan 首选是「很暗」，renao 是「人奥」，henanren 是「很安人」，但河南、热闹、河南人都在词库里，词频还不低（河南 22131、热闹 4761）。先用撇号强制切分验证：he'nan、re'nao、he'nan'ren 全部首选正确。这说明词库和 viterbi 打分都没问题，问题出在切分环节。

parser 对一串字母会返回最多 8 种切分，同音节数的几种按字母贪心排序。henan 的 hen-an 因为第一个音节 hen 比 he 长，排在 he-nan 前面。整句转换这一步只拿了排在第一的切分去组句，he-nan 这个能组出河南的切分根本没进词图参与竞争。词级候选会遍历所有切分，所以河南在候选列表里，但它是整词候选，被贪心切分组出来的「很暗」整句压到了后面。

修复只做一件事：让音节数、完整度都和首选切分相同的几种切分各跑一次整句转换，取路径分最高的一条。范围收得很窄，避免把调好的别的行为带歪：音节数不同的切分不竞争，打 xian 仍然给「先」，不会被两个音节的「西安」抢首；带缩写声母或没打完的音节不参与，简拼那套展开排序保持原样，否则 sy 会把「使用」错换成「所以」；走了模糊音或敲错边的路径不参与，手误纠错的原样词保护不受影响。落到候选上，只处理「一个覆盖整段的词库整词被贪心切分的单字硬凑整句压过」这一类，首选本就是词级整词、按词频排序的场景不动。

用撇号是用户明确指定切分，照给：hen'an 是很暗、ren'ao 是人奥，he'nan 才是河南。空格上屏和给云端的本地参考串也换成了同一套跨切分首选，保证候选、上屏、送云三处一致，选河南能按正确分词记进学习。

验证没有依赖体感。标准答案集加了 7 个锁定用例（河南、热闹、河南人，撇号的很暗/人奥/河南，以及先/西安），133 句首选率从 98.4% 升到 98.5%，没命中的仍是「行 xing」和需要云端的「什么狗屁玩意」两个老例子。另跑了一批前后鼻音边界词探针（方案、平安、天安门、生产、城市、档案、长安等），用 git stash 临时退回改动重编做基线对比，首选率完全一致，没有引入退化。core 单测 329 项、predict 44 项、server 20 项全过。剩下的 shiyi 给「是一」不给「十一」是另一个机制：它只有一种切分，是切分内部整词被高频单字组合压过，不属于这次跨切分能覆盖的范围，单独评估后再决定动不动。

## 十五、0.2.0 发布收尾：云为主定下来，旧进程加载旧 dll（10-17）

这一版把技术方向定下来，版本号从 0.1.8 提到 0.2.0。本地只留统计模型做词级排序和短词，长句纠错和整句外文交给云 DeepSeek flash，断网或超时再退回本地 opus-mt 兜底；本地中文神经模型含章彻底不移植、也不进安装包。这个决定不是拍脑袋：官方给含章自测的重排首选只有 42.5%、自由生成 51.9%，单次 130 到 200 毫秒撑不起实时上屏，云整句首选在 75.5% 左右还顺带返回外文，而含章的权重加 candle 依赖正是之前 target 冲到 30GB 的主因。本地继续追这个模型收益低、体积大、效果还不如云，砍掉更划算。

打包统一走 build.ps1，不靠手工 cargo build。脚本带 --locked 校验 Cargo.lock，ISCC 编出单文件 setup.exe，127.02MB，ProductVersion 0.2.0、ProductName 灰迹。包内有 opus-mt 离线模型、ctranslate2 运行时、词库和双架构 dll，含章模型确认已经不在包里。安装脚本里两行含章模型的 Source、README 中「端侧小模型重排」的旧描述一并清掉，避免文档和实际不符。

真机覆盖安装踩了一个隐蔽的坑。安装成功、注册表 TSF CLSID 也指向 0.2.0 双架构 dll、regsvr32 双架构退出码都是 0，但在豆包、资源管理器、Notepad++ 里按 Ctrl+空格切英文，字母照样进候选框。日志显示切到英文的标志 en=true 是对的，每一键却仍被消费、preedit 一直堆积。查进程实际加载的模块才发现，这些进程全是安装前就开着的，内存里还是 10-16 晚上手工部署的 0.1.8 dll，新 dll 落地了却没有任何进程加载。重新开一个记事本，确认它加载的是 0.2.0 dll，再测英文直通就正常了。也就是说代码没问题，是老进程没换 dll，重启后所有应用都会加载 0.2.0，旧的 0.1.8 dll 安装器已经登记重启删除。

这一版是第 3 条教训的延续，只是更隐蔽：文件落地了、注册表也对了，照样可能「源码对、真机不对」。输入法的行为要以「进程实际加载的 dll 路径和时间戳」为准，不能只看安装目录里放了什么。

## 十六、反复出现的教训（最该记住的）

1. **先找根因、确认方向再动手**，不打地鼠、不急着写代码；改几个治标没用。
2. **死路用最小探针实测证伪**——一处编辑召回、源端术语、MKL、0.6B 神经都是这样，结论留证据，避免以后重复试。
3. **真机二进制可能落后源码**：部署覆盖所有会话、核对文件时间戳；“源码对、真机不对”先怀疑部署。
4. **共享资源要隔离、要清理**：键盘布局、CLSID、管道都以注册表 / 系统实际状态为准，不靠记忆；测试引入的全局状态用 RAII 收尾。
5. **品牌与隐私有边界**：用户可见的名称、图标、视觉全部自有，内部技术标识可保留；数据默认本地，云端默认关、key 各填各的。
6. **测试要真跑、评测要干净**：留意 `#[test]` 有没有失效，评测冷启动、不学习。
7. **优先复用现成轮子和预编译产物**，不自己源码编、不重造。
8. **小步提交、每步可运行可回退**，不攒大改；打包等功能稳定后统一做，不反复打。
9. **真机验证按键链路要用物理键盘**：桌面自动化在提权 / UIPI 环境下模拟击键可能不进 TSF，候选窗是跟着鼠标位置画的悬浮窗，会造成"看似在打字"的假象；候选窗正常不等于事件进了输入法，以后台日志有没有收到按键为准。
10. **真机和对外构建必须带齐 feature、走统一构建脚本**：随手 `cargo build` 漏了 `local-nmt-system`，端侧翻译整块没接入，表现就是长句不显示译文，而源码和单测都看不出问题。判断"功能没了"先核对这一版到底是用什么命令、带什么 feature 编出来的。
11. **往 Program Files 部署要分两步**：提权只做文件替换（运行中的 exe 不能覆盖、但可以先改名再拷新的），杀进程和重启用普通身份做，保证新进程和输入法宿主同一完整性级别；每步写一个结果文件，替换完核对字节数和时间戳，别靠"脚本跑过了"判断。
